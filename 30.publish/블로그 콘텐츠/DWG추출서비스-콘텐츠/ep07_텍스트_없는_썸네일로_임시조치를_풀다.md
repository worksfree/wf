# EP07: 지울 수 없다면 안 보이게 — 도형만 남긴 썸네일로 임시 조치를 풀었다

**시리즈**: DWG 표제란/BOM 추출 서비스구축 #7
**이 글을 읽고 나면**: 렌더러가 없는 바이너리 포맷에서 "텍스트는 전혀 없이 형태만 보여주는" 미리보기를 어떻게 직접 만드는지, 그리고 화면 블러만으로는 막을 수 없는 유출 경로(다운로드)를 어떻게 별도로 처리하는지, 마지막으로 "임시 조치"를 코드 배포 없이 운영으로 되돌릴 수 있게 만드는 설계 패턴을 알 수 있습니다.

---

## 핵심 한 줄 요약
> EP05에서 "임시 조치"로 남겨뒀던 실제 고객사 도면 샘플 문제를, 진짜 파일을 지우는 대신 세 가지로 풀었다 — 텍스트가 전혀 없는 도형 윤곽선 썸네일, 결과 화면의 민감 필드 블러, 그리고 O&M에서 코드 배포 없이 샘플 자체를 바꿀 수 있는 관리 기능. 화면을 가리는 것과 데이터가 실제로 새는 경로를 막는 것은 다른 문제라는 걸 중간에 다시 깨달았다.

> **자주 묻는 질문**
> **Q. DWG를 이미지로 렌더링하는 게 그렇게 어려운가요?** → 상용 CAD 뷰어나 ODA File Converter 같은 도구엔 렌더러가 있지만, 이 서비스가 쓰는 GNU LibreDWG(오픈소스, 라이선스 이슈로 채택한 도구)엔 이미지 렌더러가 없다. JSON 덤프만 나온다.
> **Q. 그럼 어떻게 썸네일을 만들었나요?** → 이미 표제란·BOM 텍스트를 뽑으려고 파싱하던 그 JSON 안에 선분·원·호 같은 도형 엔티티 좌표도 있었다. 텍스트(MTEXT)는 전부 빼고 도형만 뽑아서 SVG로 직접 그렸다 — 새 도구를 추가한 게 아니라 이미 있던 파이프라인을 확장한 것이다.
> **Q. 화면에서만 블러 처리하면 충분한가요?** → 아니다. CSS 블러는 시각 효과일 뿐이라 DOM이나 다운로드 파일에는 원문이 그대로 남는다. 그래서 샘플 결과에서는 엑셀 다운로드 버튼 자체를 숨겨서, 블러로 가려지지 않는 유출 경로를 별도로 차단했다.

## 문제 상황

EP05에서 실제 고객사 도면 3개(이후 사용자가 직접 6개로 늘림)를 샘플 갤러리에 임시로 썼다. 당시 "임시 조치임을 기록해둔다"며 재검토 옵션까지 문서로 남겨뒀었다. 이번 편은 그 숙제를 실제로 풀러 돌아온 이야기다. 사용자의 요청은 세 가지였다 — 썸네일을 보여주되(축소판이라 구체적 내용은 어차피 안 보이니), 결과의 품명/설명은 블러 처리하고, 블러 강도와 샘플 데이터 자체를 코드 배포 없이 O&M에서 바꿀 수 있게 해달라는 것.

## STEP 1: 렌더러가 없는데 어떻게 미리보기를 만드나

가장 먼저 확인해야 할 건 기술적 실현 가능성이었다. 이 서비스가 쓰는 `dwgread.exe`(GNU LibreDWG)는 DWG를 JSON으로 덤프하는 것까지만 한다 — 이미지나 SVG를 뽑는 기능은 없다. 그런데 그 JSON 안에는 표제란·BOM 텍스트(MTEXT)뿐 아니라 도면을 실제로 그리는 도형 엔티티(LINE, ARC, CIRCLE, LWPOLYLINE)의 좌표도 고스란히 들어있었다.

```python
def _collect_geometry(objs):
    ops = []
    for o in objs:
        et = o.get("entity")
        if et == "LINE":
            s, e = o.get("start"), o.get("end")
            ops.append(("poly", [(s[0], s[1]), (e[0], e[1])]))
        elif et == "CIRCLE":
            c, r = o.get("center"), o.get("radius")
            ops.append(("circle", (c[0], c[1], r)))
        elif et == "ARC":
            # 호는 각도 구간을 직선 조각으로 근사해서 처리를 단일화한다
            ...
    return ops
```

텍스트는 아예 수집 대상에서 뺐다. 새 바이너리나 외부 라이브러리를 추가하지 않고, 이미 검증된 JSON 파싱 파이프라인만 재사용한 것이다.

## STEP 2: 첫 렌더링이 실패한 이유 — 인출선 하나가 캔버스를 망가뜨렸다

좌표를 캔버스 크기에 맞게 정규화하는 코드를 짜고 6개 샘플 도면을 전부 렌더링해봤다. 5개는 괜찮았는데, 하나(`sample_singlepart2.DWG`)가 이상했다 — 실제 부품 도형은 화면 구석의 점 하나 크기로 쪼그라들고, 화면 대부분을 커다란 삼각형 모양의 선 두 개가 차지하고 있었다.

좌표를 직접 뽑아보니 원인이 나왔다.

```
min/max X: -23.8  ~  4000.0
99 퍼센타일 X:  -5.0  ~  1985.4
```

전체 좌표 중 극히 일부(리더선 하나로 추정)가 X=4000까지 뻗어 있었다. 도면의 실제 내용은 X 0~2000 사이에 다 모여 있는데, 이 이상치 하나 때문에 "전체가 다 보이게" 맞추는 로직이 실제 내용을 화면 구석으로 몰아넣은 것이다.

해결은 단순했다 — 전체 min/max 대신 상하위 1% 퍼센타일로 맞추는 것으로 바꿨다.

```python
def _bounds(ops, trim_pct=0.01):
    xs, ys = [], []
    # ... 좌표 수집
    xs.sort(); ys.sort()
    n = len(xs)
    lo, hi = int(n * trim_pct), n - 1 - int(n * trim_pct)
    return xs[lo], xs[hi], ys[lo], ys[hi]
```

이렇게 하면 범위 밖으로 뻗은 선은 SVG viewBox 밖으로 나가 자동으로 잘려 보이지 않는다(SVG 루트 요소는 기본이 `overflow:hidden`). 다시 렌더링해보니 실제 부품 형상이 화면 대부분을 차지하고, 문제의 리더선은 모서리에 살짝 걸치는 정도로만 남았다 — Python PIL로 직접 렌더링해서 육안으로 확인했다.

## STEP 3: 큰 조립도는 그대로 그리면 안 됐다

가장 큰 샘플(`sample_top_assembly.DWG`)의 JSON을 열어보니 LINE 엔티티만 71,951개였다. 이걸 SVG `<polyline>` 하나씩으로 다 그리면 파일이 비대해지고 브라우저에서 느려진다.

```python
MAX_ENTITIES = 4000

if len(ops) > MAX_ENTITIES:
    stride = len(ops) // MAX_ENTITIES + 1
    ops = ops[::stride]
```

전체 개수 순서 그대로 등간격으로 솎아냈다 — 도면 앞부분만 자르는 게 아니라 전체에 걸쳐 고르게 샘플링되므로, 밀도는 낮아져도 전체적인 레이아웃(여러 부품 뷰가 흩어져 있는 모습)은 그대로 알아볼 수 있었다.

## STEP 4: 화면만 가려서는 안 된다는 걸 다시 깨달았다

표제란의 품명(PART NAME)과 BOM의 품명/설명 컬럼에 CSS 블러를 적용했다. 사용자가 이후 담당자(DESIGN/CHECK/APPROVE)와 도면번호(DWG NO.)도 추가로 블러 대상에 넣어달라고 요청해서, 매칭 키워드 목록만 늘리면 되는 구조라 바로 반영했다.

```javascript
const BLUR_LABEL_KEYWORDS = ["part name", "partname", "품명", "description", "design", "check", "approve", "dwg no"];
function _isBlurLabel(label) {
  const l = (label || "").toLowerCase();
  return BLUR_LABEL_KEYWORDS.some(kw => l.includes(kw));
}
```

그런데 구현하면서 짚고 넘어가야 했던 게 있었다 — CSS `filter: blur()`는 순수한 시각 효과다. DOM에는 원문이 그대로 있고, 이미 만들어져 있던 "엑셀 다운로드" 버튼을 누르면 그 원문이 고스란히 파일로 나간다. 화면만 가리고 다운로드는 그대로 열어두면, 프라이버시 조치를 했다고 착각한 채로 실제로는 아무것도 막지 못한 셈이 된다.

두 가지 선택지가 있었다 — 다운로드 파일에서도 같은 필드를 마스킹해서 내보내거나, 샘플 결과에서는 다운로드 버튼 자체를 숨기거나. 사용자와 상의해 후자로 정했다 — 샘플은 "이 도구가 이렇게 동작한다"를 보여주는 용도로만 쓰고, 실제 데이터를 파일로 가져가는 기능은 진짜 업로드에만 남겨두는 편이 더 단순하고 확실했다.

```javascript
const hasContent = entries.length || (result.bom_rows || []).length;
document.getElementById("actionsWrap").style.display = hasContent && !_isSampleResult ? "flex" : "none";
```

## STEP 5: "바꿀 수 있게 해달라"는 마지막 요청

여기까지는 지금 있는 6개 샘플을 더 안전하게 보여주는 작업이었다. 사용자의 진짜 마지막 요청은 "샘플 데이터 자체를 O&M에서, 코드 배포 없이 바꿀 수 있게 해달라"는 것이었다 — 지금 이 임시 조치가 영구히 고정되는 게 아니라, 나중에 다른 회사 데이터나 라이선스가 명확한 공개 데이터가 생기면 관리자가 직접 교체할 수 있어야 한다는 뜻이었다.

지금 샘플은 git에 커밋된 정적 파일이라 바꾸려면 코드 배포가 필요했다. 이미 관리자 페이지가 파일 업로드에 쓰고 있던 Supabase Storage 버킷을 그대로 재사용해서, 슬롯 6개(개수는 고정, 내용만 교체 가능하게 설계를 단순화) 각각에 DWG 파일과 한/영 캡션을 올릴 수 있는 새 관리 페이지를 만들었다. 파일을 새로 올리면, 앞서 만든 썸네일 생성 로직을 호출하는 새 API 경로(`/thumbnail`)를 통해 PC가 즉시 새 와이어프레임을 만들어준다.

```javascript
// 슬롯에 매니페스트 항목이 있으면 Storage 파일로, 없으면 기존 정적 샘플 그대로
const manifest = ...; // site_config에서 읽음
for (const entry of manifest) {
  const btn = document.querySelector(`.sample-card[data-slot="${entry.id}"]`);
  btn.dataset.sample = `${SAMPLE_STORAGE_BASE}/${entry.id}.dwg`;
}
```

교체하지 않은 슬롯은 배포된 기본 샘플이 그대로 유지되는 폴백 구조로 만들었다 — 관리자가 한 번에 6개를 다 바꾸지 않아도, 새 기능 자체가 기존 화면을 깨뜨리지 않는다.
