# EP06: 완성됐다고 생각했는데, 정답 데이터를 받으니 버그가 2개 더 나왔다

**시리즈**: DWG 표제란/BOM 추출 서비스구축 #6
**이 글을 읽고 나면**: 손으로 만든 몇 개의 테스트 케이스로는 절대 발견할 수 없는 버그가, 실제 정답 데이터(Ground Truth)와의 자동 대조 검증에서는 어떻게 드러나는지, 그리고 "빈 칸도 항상 자리를 차지한다"는 가정이 왜 위험한지 알 수 있습니다.

---

## 핵심 한 줄 요약
> 샘플 갤러리를 만들려고 사용자가 건네준 도면들 중 3개에는 정답 BOM 엑셀이 딸려 있었다. "당연히 잘 되겠지"라며 형식적으로 대조해봤는데, 실제로는 진짜 버그 2개가 튀어나왔다 — 하나는 열이 통째로 밀리는 오배정, 하나는 아예 다른 종류의 표를 BOM으로 착각하는 오판정이었다.

> **자주 묻는 질문**
> **Q. 이미 두 파일로 검증 완료라고 하지 않았나요?** → 맞다(EP04). 그런데 그건 "내가 고른 케이스가 우연히 다 통과하는" 상태였을 뿐이다. 새로운 도면 6개(그 중 3개는 정답까지 있는)를 받으니, 기존 테스트에 없던 조합(특정 열이 통째로 빈 도면, 부품표 아닌 다른 표가 있는 도면)이 나타났다.
> **Q. 정답 데이터가 왜 이렇게 결정적이었나요?** → 손으로 확인하면 "대충 맞아 보인다"에서 멈추기 쉬운데, 엑셀과 자동으로 셀 단위 비교를 하면 사람 눈에 안 띄는 한 칸짜리 오차까지 다 드러난다. 24행 표에서 1칸이 밀렸는지 사람이 눈으로 찾기는 어렵지만, 코드로 비교하면 즉시 나온다.
> **Q. 이 버그들을 미리 예상할 수는 없었나요?** → 어려웠을 것이다. "빈 칸도 자리를 차지한다"는 가정은 실제로 대부분의 행에서 맞았다(9칸 중 3칸이 빈 문자열로 남아있는 걸 이미 확인했었다) — 다만 "그 가정이 100%는 아니다"라는 걸 몰랐을 뿐이다. 실측 없이는 "대부분 맞다"와 "항상 맞다"를 구분할 방법이 없다.

## 문제 상황

EP05에서 샘플 갤러리를 만들기로 하고, 실제 회사 도면 몇 개를 요청했다. 사용자가 건네준 폴더를 열어보니 예상보다 훨씬 풍성했다 — 원래 요청한 3개가 아니라 6개(단품 2개, 조립도 3개, 최상위 조립도 1개)였고, 그중 조립도 3개는 **정답 BOM이 정리된 엑셀 파일까지 같이** 놓여 있었다. "bom의 ground truth는 엑셀 내용을 참고하면 된다"는 짧은 메시지 한 줄과 함께.

## STEP 1: 정답 대조 스크립트 작성

기존에는 "화면에 보이는 표가 도면과 맞아 보인다"는 육안 확인 수준이었다. 이번엔 제대로 자동 대조를 했다.

```python
def load_gt(xlsx_path):
    wb = openpyxl.load_workbook(xlsx_path, data_only=True)
    rows = list(wb.active.iter_rows(min_row=1, values_only=True))
    header = [str(c).strip() if c else "" for c in rows[0][1:10]]
    data = [[str(c).strip() if c is not None else "" for c in r[1:10]] for r in rows[1:] if r[1] is not None]
    return header, data

for name in ["sample_assembly_bom1", "sample_assembly_bom2", "sample_assembly_bom3"]:
    extracted = extract_dwg(f"{name}.DWG", DWGREAD)
    gt_header, gt_data = load_gt(f"{name}.xlsx")
    # 행 단위, 셀 단위로 정확히 비교
    ...
```

이 도면들 중 하나(`sample_assembly_bom1`)는 EP04에서 이미 24행 전부 정확하다고 확인했던 파일과 같은 내용이었다. 여기까지는 "역시 잘 되네"였다.

## STEP 2: 두 번째 파일에서 진짜 버그가 나왔다

`sample_assembly_bom2`(31행짜리 새 조립도)를 돌려보니 결과가 이랬다.

```
gt_rows=31 ext_rows=31 match_rows=28 mismatch_count=3
```

31행 중 28행은 정확했는데, 3행이 안 맞았다. 하나씩 까봤다.

**첫 번째 불일치**: 정답엔 줄바꿈이 있는 텍스트("HG-KR13B (B Type AMP, \n축방향...")인데 추출 결과는 그 줄바꿈이 공백으로 바뀌어 있었다. 이건 버그가 아니다 — 여러 줄로 쪼개진 셀 조각을 합칠 때 공백으로 이어붙이는 게 의도한 동작이었다(EP04에서 설계한 대로).

**두 번째 불일치**: 정답엔 열처리 칸에 "견적의뢰중"이라고 적혀 있는데, 추출 결과는 빈칸이었다. 원본 DWG의 실제 셀 데이터를 직접 열어보니, **그 칸 자체가 빈 문자열이었다** — DWG 안에는 없는 값이 엑셀에만 있었다. 아마 엑셀이 나중에 수동으로 업데이트되면서 DWG와 어긋난 것으로 보인다. 이것도 코드 버그는 아니다 — DWG에 없는 정보를 만들어낼 방법은 없다.

**세 번째 불일치**: 이게 진짜였다. 정답은 MATERIAL 칸이 비어있고 MAKER 칸에 "MISUMI"인데, 추출 결과는 정반대로 MATERIAL 칸에 "MISUMI"가 들어가고 MAKER 칸이 비어있었다. **값이 아예 틀린 게 아니라 엉뚱한 열에 들어간 것**이다.

## STEP 3: 원인 — "빈 칸도 항상 자리를 차지한다"는 가정이 깨졌다

문제의 행을 원본 데이터에서 직접 확인했다.

```
=== 정상 행(비교용, 9칸 전부 존재) ===
x=7.25   '28'
x=26.21  'WSSM20-6-3'
x=186.64 '와셔'
x=267.91 '2'
x=309.03 '2'
x=371.99 ''          ← MATERIAL 자리, 빈 문자열이지만 "존재"함
x=448.79 'MISUMI'    ← MAKER
x=569.72 ''          ← 표면처리
x=656.32 ''          ← 열처리

=== 문제의 행(6칸만 존재) ===
x=7.25   '30'
x=26.21  'URWL30-16-5'
x=172.53 '우레탄 와셔'
x=267.91 '2'
x=309.03 '2'
x=448.79 'MISUMI'    ← 이게 6번째 칸이라 순서대로 배정하면 MATERIAL 자리로 감
```

기존 로직은 EP04에서 "빈 칸도 SolidWorks 표 내보내기에서 빈 문자열 MTEXT로 자리를 차지한다"는 걸 실측으로 확인하고, 그 가정 위에 "행 안의 셀을 X순으로 정렬해서 순서대로 배정"하는 방식을 만들었다. 그런데 **이 행은 MATERIAL·표면처리·열처리 세 칸이 아예 존재하지 않았다** — 빈 문자열조차 없었다. 그러니 6번째로 나오는 셀(MISUMI, 원래는 MAKER=7번째 열)이 순서상 5번째 열(MATERIAL) 자리로 밀려 들어간 것이다.

## STEP 4: 수정 — 순서가 아니라 "열별 기준 위치"로 배정

순서 기반 배정을 버리고, 완전한 행(9칸이 다 있는 행)들의 열별 X좌표 중앙값을 미리 계산해서 "기준 위치"로 삼은 다음, 모든 행의 각 셀을 가장 가까운 기준 열에 배정하는 방식으로 바꿨다.

```python
complete_rows = [g for g in row_groups.values() if len(g) == n_cols]
col_xs_samples = [[group_x(row[col]) for row in complete_rows] for col in range(n_cols)]
reference_x = [sorted(s)[len(s) // 2] for s in col_xs_samples]  # 열별 중앙값

def assign_col(x):
    return min(range(n_cols), key=lambda i: abs(reference_x[i] - x))
```

이제 셀이 몇 번째로 나오는지가 아니라 "X좌표가 어느 열에 가장 가까운가"로 배정한다. 문제의 행에서 MISUMI(X=448.79)는 MATERIAL 기준 위치(X≈372)보다 MAKER 기준 위치(X≈449)에 훨씬 가깝기 때문에, 이제 정확히 MAKER로 배정된다.

## STEP 5: 다섯 번째 파일(단품 2)에서 또 다른 종류의 버그가 나왔다

BOM이 없어야 할 단품 도면 두 개도 다시 검증했다. 하나는 예상대로 "BOM 없음"이 나왔는데, 다른 하나(`sample_singlepart2`)는 **엉뚱한 표를 BOM으로 인식하고 있었다.**

```json
{"headers": ["태그", "크기", "수량"], "rows": [["", "", "+ 0.020"], ["A", "", ""], ...]}
```

"태그"/"크기"/"수량" — 이건 부품표가 아니라 **홀(구멍) 가공 치수표**였다(⌀6, M8 TAP THRU 같은 값들이 보였다). 이 도면은 부품표는 없지만, 그보다 더 큰 홀 치수표가 있었던 것이다. "MTEXT가 가장 많은 블록 = BOM"이라는 원래 가정이 무너지는 지점이었다 — 개수만으로는 표의 종류를 구분할 수 없었다.

수정은 헤더 어휘 검증을 추가하는 것이었다. 부품표에만 나오는 단어(제조사·재질·표면처리·열처리 등)가 그 블록 안에 하나라도 있어야 BOM으로 인정하게 했다. 처음엔 "수량"도 후보 단어에 넣었는데, 하필 홀 치수표에도 "수량"이 쓰여서 구분이 안 됐다 — 더 구매/가공 부품에만 의미 있는 단어로 좁혀야 했다.

```python
BOM_HEADER_KEYWORDS = [
    "part name", "partname", "품명", "품번", "부품", "material", "재질",
    "maker", "제조사", "표면처리", "열처리", "description",
]
```

## STEP 6: 최종 재검증

두 수정을 다 적용한 뒤, 6개 파일 전부 다시 돌렸다.

```
sample_assembly_bom1: 24/24 (100%, 남은 1건은 줄바꿈 표기 차이)
sample_assembly_bom2: 31/31 (남은 2건은 줄바꿈 차이·DWG-엑셀 데이터 드리프트, 코드 버그 아님)
sample_assembly_bom3: 14/14 (100%)
sample_singlepart1:   BOM 없음 (정확)
sample_singlepart2:   BOM 없음 (정확 — 홀 치수표를 더 이상 BOM으로 안 착각)
sample_top_assembly:  1/1 (100%)
```
