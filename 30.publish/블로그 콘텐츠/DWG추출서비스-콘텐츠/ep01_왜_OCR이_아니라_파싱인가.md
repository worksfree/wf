# EP01: "OCR로 도면을 읽자"는 처음부터 잘못된 질문이었다 — CAD 파일 직접 파싱으로 방향을 바꾼 이유

**시리즈**: DWG 표제란/BOM 추출 서비스구축 #1
**이 글을 읽고 나면**: CAD 도면에서 텍스트를 뽑아야 할 때 왜 OCR이 최선의 선택이 아닌지, 그리고 오픈소스 CAD 파싱 라이브러리를 실제로 선정하는 과정(라이선스 확인부터 실측 검증까지)을 알 수 있습니다.

---

## 핵심 한 줄 요약
> DWG 안의 표제란·부품표 텍스트는 이미지가 아니라 이미 정확한 좌표를 가진 벡터 텍스트다 — 이걸 이미지로 렌더링한 다음 OCR로 "다시 읽어내는" 건 원본보다 정확도가 떨어지는 우회로다. 문제는 "어떻게 더 잘 읽을까"가 아니라 "이미 있는 데이터를 어떻게 직접 꺼낼까"였다.

> **자주 묻는 질문**
> **Q. 그래도 OCR로 처리하면 안 되나요? 이미 만들어둔 OCR 서비스가 있는데.** → 기술적으로는 가능하지만, DWG를 먼저 이미지로 렌더링하는 단계 자체가 추가 실패 지점이고(렌더링 도구 필요, 해상도에 따라 화질 손실), 애초에 100% 정확한 벡터 텍스트가 있는데 굳이 그걸 흐린 픽셀로 바꾼 다음 확률적으로 다시 읽어내는 건 정확도를 스스로 깎아먹는 선택이다.
> **Q. AutoCAD 정품이 있으면 그냥 매크로로 뽑으면 되지 않나요?** → 맞다, 가장 확실한 방법이다. 다만 이 프로젝트는 "AutoCAD 없이도 동작하는 무료 웹 서비스"가 목표라 정품 라이선스에 의존하지 않는 경로가 필요했다.
> **Q. DXF로 변환하면 되는 거 아닌가요?** → 이 시리즈의 EP02에서 다루는데, 결론만 먼저 말하면 "된다고 생각했는데 조용히 데이터가 사라지는 함정이 있었다."

## 문제 상황

기구설계자가 매일 마주치는 반복 작업이 있다. 도면 표제란에서 설계자·검토자·승인자·작성일·도면번호를 옮겨 적고, BOM(부품표)을 엑셀로 정리하는 일이다. 도면 수백 장을 관리하다 보면 이 작업만으로도 상당한 시간이 든다.

이미 OCR 텍스트 추출 서비스(이 블로그 시리즈의 앞선 편들 참고)를 PC 로컬 Ollama + olmOCR-2로 구축해둔 상태였다. "이 파이프라인을 그대로 재사용해서 도면 이미지도 읽으면 되지 않을까?"가 첫 번째 아이디어였다.

그런데 실제로 도면 캡처 이미지를 놓고 생각해보니 이상했다. **표제란 글자는 도면 안에서 이미 벡터(선분·텍스트 객체)로 정확하게 존재한다.** AutoCAD로 도면을 열면 그 텍스트를 클릭해서 정확히 선택할 수 있다. 그런데 이걸 화면 캡처(래스터 이미지)로 바꾼 다음, 그 픽셀 덩어리를 다시 OCR 모델에 넣어서 "이 글자가 뭐였을까"를 확률적으로 추측하게 만드는 건 — 이미 정답을 알고 있는데 일부러 문제를 어렵게 만드는 셈이다.

## STEP 1: 확실한 방법부터 배제하기 — AutoCAD 매크로

가장 확실한 방법은 AutoCAD 자체의 AutoLISP이나 .NET API로 표제란·BOM 데이터를 직접 뽑는 것이다. 실제로 많은 기업이 이 방식을 쓴다.

다만 이 프로젝트의 목표는 "PC에 AutoCAD가 없어도, 브라우저에서 DWG 파일 하나 업로드하면 바로 결과가 나오는 무료 웹 서비스"였다. AutoCAD 정품 라이선스와 실행 환경을 전제로 하면 이 목표와 어긋난다. 배제.

## STEP 2: ODA File Converter — 가장 유력해 보였지만 라이선스가 불명확했다

DWG를 다루는 오픈소스/무료 진영에서 가장 먼저 떠오르는 이름은 **ODA(Open Design Alliance) File Converter**다. DWG 포맷 표준화 단체가 직접 배포하는 무료 변환 도구라 신뢰도가 높다고 판단했다.

그런데 실제로 다운로드 페이지를 확인해보니 예상과 달랐다.

```
curl -s "https://www.opendesign.com/guestfiles/oda_file_converter" -A "Mozilla/5.0" \
  | grep -oE 'href="[^"]*\.(exe|deb|rpm|dmg)"'
```

실제 다운로드 링크를 뽑아보니 **Windows용 실행 파일(.exe) 링크가 없었다** — Ubuntu(.deb/.rpm)와 macOS(.dmg)만 있었다. 페이지 어딘가에는 "Windows 10 이상 지원"이라는 문구가 있는데, 정작 다운로드 버튼은 리눅스/맥 전용이었다. 게다가 페이지 하단에는 "ODA 소프트웨어 60일 무료 체험" 배너가 떠 있어서, 이게 File Converter 자체의 라이선스인지 다른 상용 SDK 얘기인지 명확하지 않았다.

라이선스가 불명확한 도구를 상용 서비스에 끼워 넣을 순 없었다. 배제.

## STEP 3: GNU LibreDWG — 완전한 오픈소스(GPL)

GNU 프로젝트가 직접 관리하는 **LibreDWG**가 대안으로 남았다. GPL 라이선스로 완전히 공개돼 있고, GitHub 릴리스 페이지에서 Windows 바이너리를 직접 받을 수 있었다.

```bash
curl -s "https://api.github.com/repos/LibreDWG/libredwg/releases/latest" \
  | python -c "
import json, sys
data = json.load(sys.stdin)
for a in data['assets']:
    print(a['name'])
"
```

```
libredwg-0.14-win32.zip
libredwg-0.14-win64.zip
libredwg-0.14.tar.gz
...
```

Windows 64비트 바이너리가 GitHub 공식 릴리스로 명확하게 존재했다. 압축을 풀면 CLI 도구 여러 개가 나온다.

```
dwg2dxf.exe    dwg2SVG.exe    dwgbmp.exe    dwggrep.exe
dwglayers.exe  dwgread.exe    dwgrewrite.exe  dwgwrite.exe
dxf2dwg.exe    dxfwrite.exe
```

`dwg2dxf`(DXF로 변환), `dwgread`(DWG를 JSON/DXF 등으로 직접 덤프) 둘 다 후보였다. 실행에 필요한 DLL 4개(`libiconv-2.dll`, `libpcre2-16-0.dll`, `libpcre2-8-0.dll`, `libredwg-0.dll`, 총합 33MB)도 같은 zip 안에 들어있어 추가 설치 없이 바로 실행 가능했다.

## STEP 4: 실제로 돌아가는지 확인 — 서브프로세스 호출

Python에서 `subprocess`로 감싸는 게 가장 간단한 통합 방법이다.

```python
import subprocess
proc = subprocess.run(
    [DWGREAD_EXE, "-O", "JSON", dwg_path],
    capture_output=True,
    timeout=60,
)
if proc.returncode != 0:
    raise RuntimeError(f"dwgread 실패: {proc.stderr.decode('utf-8', 'replace')[:500]}")
```

실제 도면 파일(63KB짜리 단품 도면)로 처음 테스트했을 때 결과는 즉시 성공이었다 — 처리 시간 1초 미만, 별도 설치 과정 없음. "이거다" 싶었다.

## STEP 5: 그런데 한글이 깨져서 나왔다

첫 실행 결과를 열어보니 표제란 텍스트가 이렇게 나왔다.

```
"µµ    ¸µ   ÀÏ 2026-01-13"
```

한글이 있어야 할 자리에 알파벳+기호 뭉치가 들어있었다. 전형적인 인코딩 오사고(misdecoding) 패턴이다. DWG 파일 자체에는 한글이 CP949(한국 윈도우 기본 인코딩)로 저장돼 있는데, LibreDWG가 그 원본 바이트를 코드페이지 정보 없이 그대로 흘려보내면서, 상위 파이프라인(Python 문자열화 과정)이 그걸 Latin-1/cp1252 코드포인트로 잘못 해석해버린 것이다.

원인을 알면 되돌리기는 어렵지 않다. Python 문자열을 다시 cp1252로 인코딩해서 원래 바이트로 복원한 다음, 그 바이트를 cp949로 다시 디코드하면 된다.

```python
def fix_kr(s):
    """CP949 원본이 Latin-1 경유로 잘못 유니코드화된 문자열을 복원한다."""
    if not isinstance(s, str):
        return s
    try:
        return s.encode("cp1252").decode("cp949")
    except (UnicodeEncodeError, UnicodeDecodeError):
        return s
```

적용 후 같은 필드가 정상적으로 나왔다.

```
"작    성   일 2025-12-10"
```

(라벨 글자 사이 공백은 표제란 칸 정렬 때문에 원본에 실제로 존재하는 것 — 버그 아님.)

## STEP 6: 콘솔에 출력했는데 또 깨진다 — 그런데 이번엔 진짜 버그가 아니었다

`fix_kr()`을 적용한 결과를 Windows 콘솔에 `print()`로 찍어봤는데 여전히 깨져 보였다. "복원이 안 됐나?" 싶어 다시 파고들었는데, 실제로는 **문자열 복원 자체는 이미 성공한 상태**였다 — Python이 UTF-8로 올바르게 인코딩한 값을, Windows 콘솔이 자기 코드페이지(cp949)로 잘못 렌더링만 하고 있었을 뿐이다.

확인 방법은 콘솔 출력에 의존하지 말고 파일로 직접 쓰는 것이다.

```python
with open("result.json", "w", encoding="utf-8") as f:
    json.dump(result, f, ensure_ascii=False, indent=2)
```

이렇게 저장한 파일을 UTF-8 인식 에디터로 열어보면 한글이 정상이다. **"화면에 깨져 보인다"와 "데이터가 실제로 깨졌다"는 서로 다른 문제이고, 후자만 진짜 버그다** — 이 구분을 못 하면 이미 고친 버그를 또 고치려고 헤맬 수 있다.
