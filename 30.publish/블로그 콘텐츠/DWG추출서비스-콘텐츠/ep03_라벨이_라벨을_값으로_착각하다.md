# EP03: 표제란은 왜 방향이 일정하지 않았나 — 라벨이 라벨을 값으로 착각한 버그

**시리즈**: DWG 표제란/BOM 추출 서비스구축 #3
**이 글을 읽고 나면**: 좌표 기반으로 "라벨 옆의 값"을 찾는 알고리즘을 짤 때 흔히 걸리는 함정 세 가지 — 방향을 미리 가정하는 실수, 라벨 자신을 값 후보에서 빼먹는 실수, 그리고 반복되는 노이즈 패턴을 걸러내는 방법을 알 수 있습니다.

---

## 핵심 한 줄 요약
> 같은 표제란 안에서도 열마다 "라벨이 위에 있고 값이 아래" 또는 "값이 위에 있고 라벨이 아래"가 섞여 있었다. 방향을 하나로 가정한 알고리즘은 자기 라벨 대신 옆 라벨을, 심지어 도면 테두리의 장식용 숫자를 값으로 잘못 골랐다.

> **자주 묻는 질문**
> **Q. 왜 값 위치가 표제란 필드마다 다른가요?** → 이건 도면 작성 회사의 표제란 템플릿 디자인 문제다. 어떤 열은 "라벨 위, 값 아래"로, 어떤 열은 "값 위, 라벨 아래"로 디자인돼 있었다 — 일관성이 없는 게 아니라, 애초에 열마다 다른 레이아웃 규칙을 쓴 것이다.
> **Q. 그냥 X좌표만 맞으면 값으로 인정하면 안 되나요?** → 안 된다. 라벨 자기 자신도 X좌표가 정확히 일치하는 후보이고, 옆 라벨도 X좌표가 몇 단위 차이로 가까울 수 있다. X만 보면 라벨을 라벨로 착각하는 사고가 그대로 재현된다.
> **Q. 테두리에 있는 숫자/알파벳은 뭔가요?** → 도면 표준 표기 중 하나로, 가장자리에 1~10 숫자와 A~J 알파벳을 반복해서 붙여 "구역 참조"(예: "C-5 구역 확대") 용도로 쓴다. 표제란 값과는 무관한데, 짧고 흔해서 오탐되기 쉽다.

---

## 문제 상황

EP02에서 DWG를 JSON으로 직접 파싱하기로 결정한 뒤, 표제란(설계자·검토자·승인자·프로젝트명 등)을 뽑는 알고리즘을 짜야 했다. 문제는 표제란이 **블록 속성(ATTRIB)이 아니라 그냥 modelspace에 놓인 개별 텍스트(MTEXT)** 였다는 점이다(회사마다 표제란을 만드는 방식이 다른데, 이 회사는 이름표(태그) 없이 "DESIGN"이라는 글자와 "이재훈"이라는 글자를 각각 독립된 텍스트 객체로 배치해뒀다).

이름으로 연결이 안 되니, 남은 방법은 좌표뿐이다: "DESIGN"이라는 텍스트를 찾고, 그 근처에 있는 다른 텍스트를 값으로 채택한다.

## STEP 1: 첫 번째 시도 — "라벨 아래"로 가정

직관적으로 "라벨이 있고 그 아래 값이 있다"고 가정하고 짰다.

```python
below = [c for c in candidates if c[1] < ay - 0.5 and abs(c[0] - ax) < 20]
below.sort(key=lambda c: ay - c[1])  # Y차가 작은 것 우선
result[label] = below[0][2]
```

실제 도면으로 테스트했더니 결과가 이상했다.

```
"CHECK": "POSITIONER & STOPPER UNIT"
"APPROVE": "POSITIONER & STOPPER UNIT"
"PJT. NAME": "POSITIONER & STOPPER UNIT"
```

세 개의 서로 다른 라벨이 전부 같은 값을 물어왔다. 실제로는 CHECK는 "이재훈", APPROVE는 "임종민"이어야 했다.

## STEP 2: 원인 — X 허용 범위가 너무 넓었다

디버그 코드로 실제 좌표를 찍어봤다.

```python
anchor = next(c for c in candidates if c[2].strip() == "CHECK")
ax, ay, _ = anchor
below = [c for c in candidates if c[1] < ay - 0.5 and abs(c[0]-ax) < 20]
below.sort(key=lambda c: ay - c[1])
for c in below[:5]:
    print(f"ydiff={ay-c[1]:.2f} x={c[0]:.2f} text={c[2]!r}")
```

```
ydiff=2.36 x=127.10 text='POSITIONER & STOPPER UNIT'
ydiff=2.63 x=108.31 text='이재훈'
```

"POSITIONER & STOPPER UNIT"(PJT. NAME의 진짜 값)이 CHECK 라벨(X=108.49)보다 X좌표가 18.61만큼 떨어져 있는데도(X=127.10), 허용 범위(20 미만)에 걸려서 후보로 들어왔다. 게다가 Y차(2.36)가 진짜 값인 "이재훈"의 Y차(2.63)보다 살짝 작아서, **정렬 기준이 Y차 하나뿐이었던 탓에 X가 훨씬 먼 오답이 이겨버렸다.**

## STEP 3: 수정 — 유클리드 거리로 랭킹

X 허용 범위를 계속 좁히는 미봉책 대신, X와 Y를 같이 고려하는 실제 2차원 거리로 바꿨다.

```python
below.sort(key=lambda c: (ax - c[0]) ** 2 + (ay - c[1]) ** 2)
```

CHECK(X=108.49) 기준으로 다시 계산하면:
- "이재훈"(X=108.31, Y차=2.63): 거리² ≈ 0.03 + 6.92 = 6.95
- "POSITIONER..."(X=127.10, Y차=2.36): 거리² ≈ 346 + 5.57 = 352

이제 "이재훈"이 압도적으로 가깝게 나온다. 재실행하니 CHECK/APPROVE 둘 다 정상으로 나왔다.

## STEP 4: 그런데 PJT. NAME이 여전히 틀렸다

CHECK/APPROVE는 고쳤는데, PJT. NAME은 여전히 "UNIT NAME"(다른 필드의 **라벨 텍스트 자체**)을 값으로 물어왔다.

디버그해보니 이유가 명확했다. "UNIT NAME"이라는 라벨은 PJT. NAME 라벨(X=123.84, Y=12.74)의 거의 바로 아래(X=123.88, Y=9.99)에 위치해 있었다 — 각도 정렬은 다른 필드의 라벨인데, 순수 유클리드 거리로는 진짜 값("전동콤프 스크롤 베어링 조립기", 좀 더 먼 위치)보다 오히려 더 가까웠다.

원인은 명확했다 — **후보 목록에서 "다른 라벨 자신의 텍스트"를 제외하지 않고 있었다.**

```python
label_set = {lb.strip() for lb in labels}
others = [
    c for c in candidates
    if c[2].strip() not in label_set and (c[0], c[1]) != (ax, ay)
]
```

라벨 텍스트 자체를 후보에서 아예 빼버리니, 그제서야 진짜 값을 정확히 찾았다.

## STEP 5: 방향(위/아래) 가정 자체를 버렸다

라벨 배제 로직을 넣고도 한 가지 필드(DWG NO.)가 계속 틀렸다. 다시 디버그해보니, 이 필드는 **값이 라벨보다 아래가 아니라 살짝 위**에 있었다(라벨 Y=4.49, 값 Y=4.74 — 값이 라벨보다 0.25 높음). "값은 아래에 있다"는 처음의 가정 자체가 이 필드에는 안 맞았던 것이다.

같은 표제란 안에서 DESIGN/CHECK/APPROVE 열은 "값이 아래", PJT. NAME/UNIT NAME/PART NAME/DWG NO. 열은 "값이 위" — **열마다 배치 관례가 정반대였다.** 방향을 미리 정하지 않고, 순수하게 가장 가까운 후보를 찾는 방식으로 최종 정리했다.

```python
others = [
    c for c in candidates
    if c[2].strip() not in label_set and (c[0], c[1]) != (ax, ay)
]
others.sort(key=lambda c: (ax - c[0]) ** 2 + (ay - c[1]) ** 2)
result[label] = others[0][2]
```

## STEP 6: 마지막 함정 — 도면 테두리의 "장식용 숫자"

여기까지 고치고 나니 12개 필드 중 11개가 정확했는데, TREATMENT(표면처리)만 "CHROME"이 아니라 "7"이라는 뜬금없는 값이 나왔다. 디버그 결과:

```
dist=1.91 x=119.10 y=103.58 text='7'
dist=2.61 x=119.57 y=99.09 text='CHROME'
```

진짜 값(CHROME)보다 "7"이라는 숫자가 아주 살짝(0.7 정도) 더 가까웠다. 이 "7"의 정체는 도면 테두리에 반복적으로 붙는 **구역 참조 그리드**(위/아래 가장자리에 1~10, 좌/우 가장자리에 A~J를 반복 표기하는 도면 표준 표기법)의 일부였다.

이건 좌표만으로는 걸러낼 수 없다 — 대신 "짧은 숫자/알파벳 하나짜리 텍스트가 같은 Y(또는 X)에 5개 이상 반복되면 그리드로 간주하고 제외"하는 패턴 기반 필터를 추가했다.

```python
def _is_short_token(t):
    t = t.strip()
    return bool(t) and len(t) <= 2 and (t.isdigit() or t.isalpha())

y_counts = Counter(round(y, 0) for x, y, t in candidates if _is_short_token(t))
grid_ys = {y for y, n in y_counts.items() if n >= 5}
candidates = [c for c in candidates if not (_is_short_token(c[2]) and round(c[1], 0) in grid_ys)]
```

이후 12개 필드 전부 정확하게 나왔다.
