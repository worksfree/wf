# EP12: 위치는 아는데 글자는 못 믿는 모델 — 두 모델을 섞어야 했던 이유

**시리즈**: OCR 서비스구축 #12
**이 글을 읽고 나면**: 하나의 모델로 "위치 탐지"와 "글자 인식"을 동시에 잘하기 어려울 때, 서로 다른 두 모델을 역할 분담시켜 조합하는 하이브리드 설계 패턴과, 같은 모델의 서로 다른 두 번 호출 결과를 비교할 때 겪을 수 있는 미묘한 문자열 불일치 문제를 알 수 있습니다.

---

## 핵심 한 줄 요약
> "인식된 글자 위치를 이미지 위에 표시해서 오타를 바로 고칠 수 있게 해달라"는 요청에, 위치 탐지 전용 모델(EasyOCR)로 박스만 찾고, 그 박스를 클릭하면 크롭한 영역을 이미 검증된 인식 모델(olmOCR-2)로 다시 읽는 하이브리드 구조로 답했다 — 한 모델이 위치도 글자도 다 잘하길 기대하는 대신, 잘하는 일만 시켰다.

> **자주 묻는 질문**
> **Q. EasyOCR이 인식한 글자를 그냥 쓰면 안 되나요?** → 실측해보니 EasyOCR 자체 인식 텍스트는 신뢰도(confidence)가 0.1~0.3대로 낮게 나오는 경우가 많았다. 위치(바운딩 박스)는 안정적으로 잘 찾는데, 그 박스 안 글자를 읽는 정확도는 이미 검증된 olmOCR-2에 크게 못 미쳤다.
> **Q. PaddleOCR을 쓰면 위치·인식 둘 다 되지 않나요?** → 시도했다. 그런데 이 PC(RTX 5090, Windows)에서 PaddlePaddle 실행기 자체가 기본 텍스트 탐지 단계에서부터 크래시하는 프레임워크 버그에 걸려 완전히 배제했다 — 레이아웃 분석뿐 아니라 가장 단순한 기능조차 못 썼다.
> **Q. 두 번 호출하면 느리지 않나요?** → 위치 탐지는 박스를 클릭했을 때만, 그것도 클릭한 영역만 크롭해서 다시 인식하기 때문에 전체 이미지를 두 번 처리하는 것보다 훨씬 가볍다. 게다가 위치 탐지 자체는 GPU/Ollama를 쓰지 않아 요청 제한(rate limit) 대상에서도 뺐다.

## 문제 상황

OCR 결과에 오타가 있을 때, 사용자가 원본 이미지의 어느 부분이 그 텍스트였는지 확인하고 수정할 수 있으면 좋겠다는 요청을 받았다. "인식된 글자 위치를 이미지 위에 표시"하려면, 먼저 "이 이미지의 어디에 어떤 글자가 있는지"를 알아야 한다.

## STEP 1: 후보 모델 탐색 — 전부 한 모델로 되면 좋겠지만

이상적으로는 하나의 모델이 위치와 텍스트를 동시에 정확하게 뽑아주면 좋았다. 기존에 검증된 olmOCR-2는 바운딩 박스 좌표를 출력하는 기능이 없었다(순수 텍스트 추출 전용으로 검증된 모델이라). 위치 정보까지 주는 모델을 따로 찾아야 했다.

**PaddleOCR**: 위치 탐지(det) + 인식(rec) + 레이아웃 분석까지 다 되는 걸로 알려진 라이브러리라 가장 먼저 시도했다. 그런데 가장 기본적인 텍스트 탐지 단계에서부터 이 PC에서 크래시했다.

```
ConvertPirAttribute2RuntimeAttribute not support
[pir::ArrayAttribute<pir::DoubleAttribute>]
```

PaddlePaddle 3.x의 PIR/oneDNN 실행기 내부 버그였다 — mkldnn 비활성화 등 여러 우회를 시도했지만 프레임워크 자체의 문제라 고칠 수 있는 범위가 아니었다. 완전히 배제.

**Tesseract.js**: 브라우저에서 바로 실행되는 WASM OCR이라 새 서버 인프라가 필요 없다는 장점이 있어 시도했다. 그런데 한글 문서에서 박스 자체가 글자 단위로 깨져 나왔다(박스 하나가 한 음절도 아니고 자모 단위로 쪼개지는 경우가 흔했음) — 위치 정보 자체를 신뢰할 수 없는 수준이라 배제.

**EasyOCR**: CPU로도 동작하고(GPU 없이), 위치(바운딩 박스) 탐지는 안정적으로 잘 나왔다. 다만 박스 안 텍스트 자체의 인식 신뢰도가 낮았다(0.1~0.3대 다발).

## STEP 2: "위치만 믿고 글자는 안 믿는" 하이브리드 구조로 결정

EasyOCR이 유일하게 위치 탐지만큼은 안정적이었다는 점에서, 역할을 분리하기로 했다.

```
1. EasyOCR: 이미지 전체에서 텍스트 박스 위치만 탐지 (자체 인식 텍스트는 참고용으로만 반환)
2. 사용자가 박스를 클릭
3. 그 박스 영역만 원본 이미지에서 크롭
4. 크롭한 이미지를 이미 검증된 olmOCR-2(/ocr 엔드포인트)로 다시 인식
5. 그 결과를 편집 가능한 텍스트로 보여줌
```

PC 로컬에 EasyOCR 전용 소형 HTTP 서버를 새로 만들었다. 기존 Ollama(포트 8765)와는 완전히 별개 프로세스다.

```python
reader = easyocr.Reader(["ko", "en"], gpu=False)

def do_POST(self):
    if self.path == "/detect":
        img = np.array(Image.open(io.BytesIO(img_bytes)).convert("RGB"))
        results = reader.readtext(img)
        boxes = [{
            "x0": min(xs), "y0": min(ys), "x1": max(xs), "y1": max(ys),
            "hint_text": text, "hint_confidence": float(conf),  # 참고용, 신뢰 안 함
        } for box, text, conf in results]
        self._send_json({"ok": True, "boxes": boxes})
```

`hint_text`/`hint_confidence`라는 이름 자체가 설계 의도를 드러낸다 — "참고용 힌트일 뿐, 이 값을 최종 결과로 쓰지 않는다"는 걸 변수명에 박아뒀다.

## STEP 3: 원상복구 가능하게 — 기존 워크플로우는 그대로 두고 토글로 분리

이 기능은 새 인프라(PC 로컬 EasyOCR 서버, Cloudflare Tunnel 라우팅)에 의존한다. "이 로컬 서버를 그냥 끄면 기존 OCR 흐름에 전혀 영향이 없어야 한다"는 요구사항이 있었다.

이 체크박스를 끄면 기존 OCR 파이프라인만 그대로 동작한다. 켜져 있어도 PC의 감지 서버가 꺼져 있으면 "오프라인" 안내만 뜨고, 나머지 기능(텍스트 추출·엑셀 저장 등)은 전혀 영향받지 않는다. 나중에 유료 등급 전용으로 제한할 계획도 있어서, 게이트 함수를 미리 분리해뒀다.

## STEP 4: 미리보기와 오버레이를 하나로 합치기

처음 버전은 원본 미리보기와 박스 오버레이가 별도의 이미지 엘리먼트였다(오버레이용 이미지를 따로 하나 더 그려서 그 위에 박스를 얹는 방식). 실사용해보니 "그냥 원래 미리보기 위에 바로 박스가 뜨면 안 되나?"라는 피드백을 받았다. 맞는 지적이라, 중복 이미지 엘리먼트를 없애고 기존 미리보기 위에 직접 박스를 그리는 구조로 다시 짰다.

```css
.preview-img-wrap { position: relative; } /* 이 안에 이미지 + 박스들이 같이 존재 */
.overlay-box { position: absolute; border: 2px solid #3b82f6; }
```

박스 좌표를 퍼센트 단위로 저장해두면, 미리보기를 확대/축소해도(`width: X%`) 별도 재계산 없이 박스도 같이 늘어나고 줄어든다 — 부모 래퍼의 너비만 바뀌면 안의 절대 위치 자식들도 같은 비율로 따라간다.

## STEP 5: 편집한 텍스트를 본문에 반영할 때 생긴 함정

박스를 클릭해서 나온 크롭 텍스트를 수정한 다음 "본문에 반영" 버튼을 누르면, 전체 결과 텍스트에서 원래 인식됐던 문구를 찾아 수정된 텍스트로 바꿔치기하는 기능도 추가했다. 그런데 실사용 중 "주소: 경기 수원시..."(크롭 재인식 결과, 콜론 뒤에만 공백)를 편집한 뒤 반영하려니 "본문에서 원래 문구를 찾지 못했습니다"라는 에러가 났다.

원인은 같은 모델이 같은 영역을 두 번 다르게 인식했기 때문이었다 — 전체 이미지를 인식했을 때는 "주소 : ..."(콜론 **앞뒤** 공백), 크롭만 다시 인식했을 때는 "주소: ..."(콜론 **뒤**만 공백)였다. 똑같은 모델인데 문맥(전체 페이지 vs 고립된 크롭)이 다르면 공백 하나 정도는 미묘하게 다르게 뱉을 수 있다는 뜻이다.

첫 수정은 "검색어 안의 공백만 `\s*`로 바꾸는" 정규식이었는데, 재현 테스트를 직접 돌려보니 이 방식으로는 정확히 이 사례(본문에만 공백이 더 있는 경우)를 못 잡는다는 걸 발견했다. 최종적으로는 양쪽 문자열에서 공백을 전부 제거하고 비교한 다음, 일치한 위치를 원본 문자열의 인덱스로 역매핑하는 방식으로 바꿨다.

```javascript
function findWhitespaceFlexibleMatch(haystack, needle) {
  const strippedNeedle = needle.replace(/\s+/g, "");
  const strippedChars = [];
  const origIndex = [];
  for (let i = 0; i < haystack.length; i++) {
    if (!/\s/.test(haystack[i])) { strippedChars.push(haystack[i]); origIndex.push(i); }
  }
  const pos = strippedChars.join("").indexOf(strippedNeedle);
  if (pos === -1) return null;
  return { start: origIndex[pos], end: origIndex[pos + strippedNeedle.length - 1] + 1 };
}
```

이 방식은 공백이 어느 쪽에 더 있든(검색어 쪽이든 본문 쪽이든) 상관없이 정확히 매칭된다 — 검증을 위해 만든 재현 테스트 케이스로 실제 확인했다.
