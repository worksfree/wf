# EP03: "회전 버튼까지 만들었는데 진짜 원인은 해상도였다" — 컨텍스트 예산 초과 버그 발견기

**시리즈**: OCR 서비스구축 #3
**이 글을 읽고 나면**: VLM(비전 언어 모델)에 이미지를 보낼 때 해상도를 그냥 원본 그대로 보내면 안 되는 이유와, "회전 문제처럼 보이는 증상"의 진짜 원인을 진단하는 방법을 알 수 있습니다.

---

## 핵심 한 줄 요약
> 스마트폰 원본 사진(4000x3000, 12MP)을 그대로 보내면 비전 인코더가 소모하는 토큰이 모델의 컨텍스트 예산을 넘어서 응답이 몇 글자만에 끊긴다 — 회전 문제로 착각하기 딱 좋은 증상이다.

> **자주 묻는 질문**
> **Q. 사진을 아무리 돌려도 결과가 이상하면 뭘 의심해야 하나요?** → 먼저 원본 해상도부터 확인한다. 4000px 이상이면 다운스케일부터 시도해본다.
> **Q. 해상도를 낮추면 정확도가 떨어지지 않나요?** → 오히려 반대다. 모델이 처리 가능한 범위를 벗어나면 아예 응답이 끊기므로, "적당히 낮춰서 완전히 처리되는 것"이 "과도하게 커서 중간에 끊기는 것"보다 낫다.
> **Q. num_ctx를 무조건 크게 잡으면 되지 않나요?** → VRAM 사용량이 같이 늘고, 실측으로는 오히려 3배 해상도 + 큰 컨텍스트 조합에서 정확도가 급락한 사례도 있었다(모델이 처리해본 적 없는 크기라 그런 것으로 추정).

---

## 문제 상황

OCR 페이지에 "🔄 회전 후 다시 인식" 버튼을 만들어 배포했다. 그런데 실사용 테스트 중, 손으로 든 채 찍은 카드 매출전표 사진을 올렸더니 인식 결과가 11자만 나오고 끊겼다. 처음엔 당연히 "사진이 회전돼 있어서 그런가?" 싶었다.

---

## STEP 1: 잘못된 가설부터 세워보기

원본 이미지를 90도씩 돌려가며 세 방향 다 테스트했다.

```python
for angle, code in [('cw90', cv2.ROTATE_90_CLOCKWISE),
                     ('ccw90', cv2.ROTATE_90_COUNTERCLOCKWISE),
                     ('180', cv2.ROTATE_180)]:
    rot = cv2.rotate(img, code)
    # OCR 호출...
```

결과: **세 방향 다 똑같이 14자에서 끊겼다.** 회전 방향이 문제였다면 최소 한 방향은 정상이어야 하는데, 전부 동일하게 실패했다 — 이건 회전이 원인이 아니라는 강력한 신호다.

---

## STEP 2: 진짜 원인 찾기 — Raw 응답 뜯어보기

```python
resp, elapsed, raw = ollama_generate(model, prompt, [b64], options={'num_predict': 500})
print('eval_count', raw.get('eval_count'), 'done_reason', raw.get('done_reason'))
```

```
eval_count: 14
done_reason: length
```

`num_predict`를 500으로 넉넉히 줬는데 `done_reason`이 `length`로 겨우 14토큰만에 끝났다. **`length`는 "출력 한도 초과"를 뜻하는데, 14토큰이면 아직 한도에 한참 못 미친다** — 이건 `num_predict`가 아니라 **모델의 전체 컨텍스트(num_ctx)가 이미 꽉 찼다**는 뜻이었다.

```python
img = cv2.imread('receipt.jpg')
print(img.shape)  # (4000, 3000, 3)
```

원본이 **4000x3000, 12메가픽셀**이었다. 이 사진을 비전 인코더에 넣으면 그것만으로 수천 개의 "비전 토큰"이 생기고, 모델의 기본 컨텍스트(대개 4096)를 프롬프트만으로 거의 다 써버린다 — 실제로 답변을 생성할 토큰이 남지 않았던 것이다.

---

## STEP 3: 다운스케일로 검증

```python
def downscale_max(img, max_dim=1600):
    h, w = img.shape[:2]
    m = max(h, w)
    if m <= max_dim: return img
    s = max_dim / m
    return cv2.resize(img, (int(w*s), int(h*s)), interpolation=cv2.INTER_AREA)
```

같은 사진을 1600px로 줄여서 다시 보냈다.

```
prompt_tokens: 2518   (기존: 컨텍스트 초과로 계산 불가)
done_reason: stop      (기존: length)
CER: 0.36               (기존: 0.97 — 사실상 실패)
```

정상적으로 끝까지 처리됐다. 회전은 애초에 문제가 아니었다.

---

## STEP 4: 프로덕션에 반영 — 클라이언트 다운스케일 + 서버 컨텍스트 확대

두 군데를 같이 손봤다.

**클라이언트(브라우저)** — 회전 캔버스를 그릴 때 긴 변을 1800px로 제한:

```js
const MAX_OCR_DIM = 1800;
function rotateImageToBase64(img, degrees) {
  // ...
  const maxDim = Math.max(canvasW, canvasH);
  if (maxDim > MAX_OCR_DIM) {
    const scale = MAX_OCR_DIM / maxDim;
    drawW *= scale; drawH *= scale;
    canvasW *= scale; canvasH *= scale;
  }
  // ...
}
```

**Cloudflare Worker** — 다운스케일해도 여유가 빠듯할 수 있어 컨텍스트를 넉넉히:

```js
const BASE_OPTIONS = { temperature: 0, num_predict: 3000, num_ctx: 6144 };
```

## STEP 5: "그럼 해상도를 더 높이면 더 잘 되지 않을까?" — 아니었다

혹시나 해서 3배 해상도(1785x2526) + `num_ctx: 8192`로도 테스트했다.

```
prompt_tokens: 4116
CER: 0.70   (2배 해상도 대비 CER 0.19 → 0.70로 오히려 급락)
```

컨텍스트만 늘려서 처리는 됐지만, 모델이 학습 과정에서 접해본 적 드문 해상도라 그런지 정확도가 오히려 크게 떨어졌다. **"처리 가능한 최대치"와 "정확도가 가장 좋은 지점"은 다르다** — 실측으로 2배(약 1200~1800px) 부근이 이 모델의 실질적 최적점이었다.
