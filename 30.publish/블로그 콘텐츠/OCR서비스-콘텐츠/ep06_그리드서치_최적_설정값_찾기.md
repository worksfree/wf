# EP06: "대비 +15%, 샤프니스 25%"는 어디서 나온 숫자였나 — 그리드 서치로 최적값 찾기

**시리즈**: OCR 서비스구축 #6
**이 글을 읽고 나면**: 이미지 전처리(대비·샤프니스) 파라미터를 감으로 정하지 않고 실측으로 찾는 2단계 그리드 서치 방법론과, "기본값 하나가 모든 문서 유형에 맞을 거라는 가정"이 왜 틀렸는지 알 수 있습니다.

---

## 핵심 한 줄 요약
> 대비(콘트라스트)와 샤프니스는 슬라이더로 조절 가능하게 만들어뒀지만, 기본값(+15%/25%)은 사실 감으로 정한 숫자였다. 손글씨·긴 문서·영수증 6개 실측 표본으로 7×7 그리드(49조합)를 전수 탐색한 뒤 5×5(25조합) 정밀 탐색을 이어붙이는 2단계 방식으로 카테고리별 진짜 최적값을 찾았더니, 세 카테고리 전부 기본값과 다른 방향이었다.

> **자주 묻는 질문**
> **Q. 왜 한 번에 촘촘하게 탐색하지 않고 2단계로 나눴나요?** → 대비×샤프니스 조합 전체를 촘촘하게(예: 1% 단위) 훑으면 호출 수가 기하급수적으로 늘어난다. 먼저 성긴 격자(7×7=49)로 대략적인 최적 구역을 찾고, 그 구역 주변만 촘촘하게(5×5=25) 다시 훑으면 정확도는 거의 유지하면서 호출 수를 크게 줄일 수 있다.
> **Q. 6개 표본이면 너무 적지 않나요?** → 맞다, 그래서 이 편의 결과는 "방향성 참고용"이라고 명시했다. 표본을 AI-Hub 공개 데이터로 확장해서 재검증한 이야기는 다음 편(EP07)에서 다룬다.
> **Q. temperature=0인데 왜 같은 설정을 여러 번 안 돌려봤나요?** → temperature=0은 모델이 결정론적으로(항상 같은 입력엔 같은 출력을) 동작한다는 뜻이라, 반복 샘플링으로 편차를 줄일 필요가 없다. 그리드의 각 점은 1회 호출로 충분했다 — 덕분에 촘촘한 탐색에 드는 비용을 아낄 수 있었다.

## 문제 상황

OCR 서비스 UI에 대비·샤프니스 슬라이더를 만들면서, 기본값을 얼마로 둘지가 문제였다. "대충 무난해 보이는 값"으로 +15%/25%를 정했는데, 이게 실제로 인식 정확도에 도움이 되는 값인지 검증한 적이 없었다. 슬라이더를 만들어놓고 기본값을 근거 없이 정하는 건 앞뒤가 안 맞았다.

## STEP 1: 채점 기준 — CER(문자 오류율)

정답 텍스트가 있는 이미지 6장(손글씨 2장, 긴 문서 2장, 영수증 2장 — 이미 로컬에 있던 실측 표본)을 채점 대상으로 정했다. 채점 지표는 CER(Character Error Rate, 문자 오류율)이다 — 인식 결과와 정답 텍스트를 문자 단위로 비교해서, 틀린 문자 비율을 계산한다. 0에 가까울수록 정확하다.

```python
    ...
```

## STEP 2: 1단계 — 성긴 그리드(coarse) 49조합 전수 탐색

콘트라스트 7단계 × 샤프니스 7단계 = 49조합을 6개 이미지 각각에 다 돌렸다(6 × 49 = 294회 호출). 각 조합마다 실제 프로덕션과 동일한 파이프라인(같은 모델 `richardyoung/olmocr2:7b-q8`, 같은 옵션)을 그대로 재현해서, 실측 결과가 실제 서비스 동작과 어긋나지 않게 했다.

카테고리별(같은 카테고리 이미지 2장의 평균 CER) 1단계 최적점:

```
handwriting: 콘트라스트 -20%, 샤프니스 80%  →  CER 0.0204
longdoc:     콘트라스트 -10%, 샤프니스  0%  →  CER 0.1326
receipt:     콘트라스트 -10%, 샤프니스 15%  →  CER 0.1917
```

이 시점에 이미 흥미로운 패턴이 보였다 — **세 카테고리 다 콘트라스트를 낮추는 방향(-10~-20%)이 최적**이었다. 기본값(+15%, 올리는 방향)과는 정반대였다.

## STEP 3: 2단계 — 1단계 최적점 주변을 정밀 탐색(fine)

1단계에서 찾은 대략적인 위치 주변에서, 더 촘촘한 5×5(25조합)로 재탐색했다(6 × 25 = 150회 호출). 성긴 격자가 "대충 이 근방"을 알려줬다면, 정밀 탐색은 "정확히 몇 %가 최선인지"를 찾는 단계다.

```
handwriting: 콘트라스트 -20%, 샤프니스 73%  →  CER 0.0204 (1단계 대비 개선 없음 — 이미 근접했던 것)
longdoc:     콘트라스트 -10%, 샤프니스  0%  →  CER 0.1326 (동일 유지)
receipt:     콘트라스트 -20%, 샤프니스  8%  →  CER 0.1885 (1단계보다 개선: 0.1917 → 0.1885)
```

손글씨·긴 문서는 1단계에서 이미 정확한 지점에 근접해 있었고, 영수증만 정밀 탐색으로 소폭 개선됐다(-10%→-20%로 방향이 더 뚜렷해짐).

## STEP 4: 실패/스킵 0건 — 안정성도 같이 확인

```
총 호출: 404건 (294 + 150 — 일부 겹치는 지점 제외 실 호출 수)
실패/스킵된 호출: 0건
```

파라미터를 극단적으로 밀어붙인 조합(콘트라스트 -20%, 샤프니스 100% 등)에서도 서버 타임아웃이나 모델 오류 없이 전부 응답을 받았다. 파이프라인 안정성 자체는 문제가 없다는 뜻이라, 순수하게 "어떤 값이 정확도에 유리한가"에만 집중해서 결과를 해석할 수 있었다.

## STEP 5: 왜 대비를 낮추는 게 더 나았을까 — 추정 근거

수치만 봐서는 이유를 알 수 없어서, 실제 이미지를 각 설정으로 렌더링해서 육안으로 비교했다. 콘트라스트를 과하게 올리면(+30~50%) 흐릿하거나 연필로 쓴 획의 옅은 부분이 아예 끊겨버리는 게 보였다 — 대비를 높인다는 게 "선명해진다"보다는 "밝은 곳은 더 밝게, 어두운 곳은 더 어둡게"라, 원래도 연했던 부분이 배경에 완전히 묻혀버린 것이다. 반대로 대비를 살짝 낮추면 그 연한 획까지 회색조로 살아남아서, 모델이 원본의 미묘한 뉘앙스를 더 잘 읽어낸 것으로 추정된다.

긴 문서(벡터 렌더링된 PDF)의 경우 샤프니스 0%(끄기)가 최적이었던 것도 비슷한 이유로 추정한다 — 이미 선명한 벡터 텍스트에 샤프닝(언샵 마스크)을 걸면, 없던 경계가 인위적으로 생기면서 오히려 아티팩트가 늘어나는 것으로 보인다.

## STEP 6: 이 결과를 프로덕션에 바로 반영하지 않은 이유

카테고리별 최적값을 확인했지만, 슬라이더 기본값을 바로 이 값으로 바꾸지는 않았다. 표본이 카테고리당 2개뿐이라, "이 6장에서는 이 값이 최선이었다"를 넘어 "모든 손글씨/영수증에 일반화된다"고 주장하기엔 근거가 얕았기 때문이다. 대신 이 결과는 **문서 유형 프리셋**(다음다음 편에서 다룰 기능)의 초기값으로 쓰고, 별도의 더 큰 검증 데이터셋(AI-Hub)으로 재확인하는 절차를 거치기로 했다 — 그 이야기는 EP07에서 이어진다.
