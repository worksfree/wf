# EP10: 텍스트로는 다 나오는데 엑셀은 왜 비는가 — 구조화의 조용한 실패

**시리즈**: OCR 서비스구축 #10
**이 글을 읽고 나면**: "자유 텍스트 인식"과 "구조화된 필드 추출"이 왜 같은 모델을 쓰고도 정확도가 크게 벌어질 수 있는지, 그리고 LLM 구조화 결과를 정규식 안전망으로 보완하는 실용적인 패턴을 알 수 있습니다.

---

## 핵심 한 줄 요약
> 같은 영수증, 같은 모델(olmOCR-2)인데 출력을 "텍스트"로 하면 거의 모든 정보가 나오고, "엑셀"로 하면 상호명과 합계만 남고 나머지가 텅 비었다. 원인은 2단계 구조화(자유 텍스트 → JSON 필드)가 JSON 파싱 자체는 성공해서 에러 없이 넘어가지만, 필드를 골고루 채우지 못하는 조용한 실패였다.

> **자주 묻는 질문**
> **Q. 왜 텍스트를 한 번에 JSON으로 안 뽑고 2단계로 나눴나요?** → 이미 실측으로 정확도가 검증된 자유 텍스트 추출 프롬프트를 그대로 재사용할 수 있고, "이미지 + 문법제약 디코딩(JSON Schema)"을 한 번에 하는 조합은 이 프로젝트에서 검증된 적이 없어 리스크가 컸다. 이미 정확도가 검증된 텍스트에서 구조만 뽑아내는 게 더 안전하다고 판단했다.
> **Q. 재시도를 넣으면 해결되지 않나요?** → 안 된다. 재시도 로직은 "에러가 났을 때" 발동하는데, 이 버그는 JSON 파싱이 성공(에러 없음)한 상태로 필드만 비어서 나온다 — 재시도를 걸 조건 자체가 성립하지 않는 실패 유형이다.
> **Q. 정규식으로 다 뽑을 수 있으면 애초에 LLM이 왜 필요한가요?** → 정규식은 라벨이 뚜렷하고 형식이 고정적인 필드(사업자번호, 전화번호, 날짜, 주소)에서만 안정적이다. 품목명·수량·가격처럼 형식이 자유로운 부분은 LLM의 문맥 이해가 여전히 필요하다. 이번 수정은 "LLM을 정규식으로 대체"가 아니라 "LLM이 놓친 자리를 정규식으로 메우는" 보완이다.

---

## 문제 상황

영수증 키/밸류 추출 기능을 만들면서, OCR 파이프라인은 이미 검증된 자유 텍스트 추출을 그대로 쓰고, 그 텍스트를 다시 한 번 모델에 넣어 JSON 스키마로 구조화하는 2단계 설계를 했다.

```
1단계: 이미지 → 자유 텍스트 (이미 검증된 프롬프트 그대로 재사용)
2단계: 텍스트만(이미지 없이) → JSON 구조화 (Ollama format 파라미터로 스키마 강제)
```

사용자가 실사용 테스트 중 이상한 걸 발견했다. 같은 영수증을 출력 형식만 "텍스트"에서 "엑셀"로 바꿔서 처리했더니, 텍스트에서는 상호명·사업자번호·전화·주소·거래일시·품목·합계까지 거의 다 나왔는데, 엑셀에서는 상호명과 합계 딱 두 개만 채워지고 나머지는 전부 빈칸이었다.

## STEP 1: 재시도가 안 걸린 이유부터 확인

2단계 구조화 코드에는 이미 재시도 로직이 있었다.

```javascript
try {
  structured = await structureReceipt(env, ocrResult.text, { temperature: 0 });
} catch (e) {
  // JSON 파싱 실패·반복 폭주 시 penalty 걸고 재시도
  structured = await structureReceipt(env, ocrResult.text, { repeat_penalty: 1.3, ... });
}
```

그런데 로그를 확인해보니 재시도가 **한 번도 발동하지 않았다.** `structureReceipt()`가 예외를 던지지 않고 정상적으로 리턴했기 때문이다 — JSON 파싱 자체는 성공했다. 문제는 파싱된 JSON 안의 값이 비어있었다는 것이다.

```json
{
  "store_name": "삼성우리신경외과의원",
  "business_reg_no": "",
  "date": "",
  "phone": "",
  "address": "",
  "items": [],
  "total": 181400
}
```

**에러 없이, 형식은 맞게, 그런데 내용은 골고루 안 채워진 상태로 조용히 끝났다.** 이건 "실패"로 분류되지 않는 실패라, 기존 에러 핸들링(재시도)이 아예 발동할 조건이 안 됐다.

## STEP 2: 원본 텍스트에는 데이터가 다 있었다

1단계에서 뽑힌 자유 텍스트를 다시 확인해보니, 필요한 정보가 전부 들어있었다.

```
상호: 삼성우리신경외과의원 대표자: 김기준
사업자번호: 501-93-01969 TEL: 031-224-5777
주소: 경기 수원시 팔달구 효원로 278 (인계동)
거래일시: 26/07/08 17:38:27
...
총 합 계: 181,400 원
```

1단계 텍스트 추출은 완벽했다. 2단계(같은 텍스트를 다시 모델에 넣어 JSON으로 구조화)에서만 필드를 놓쳤다 — **같은 모델이 같은 정보를 두고, 자유 텍스트로 뱉을 때는 다 뱉고 JSON 스키마로 뱉을 때는 일부만 뱉은 것**이다. 구조화 단계 자체가 무언가를 놓치기 쉬운 조건이라는 뜻이다.

## STEP 3: 안전망 — 정규식으로 직접 뽑아서 빈 자리만 메운다

모델의 2단계 구조화가 근본적으로 왜 이런지(디코딩 제약과 프롬프트 상호작용 문제로 추정) 깊이 파고들기보다, 실용적인 안전망을 먼저 세우기로 했다. 라벨이 뚜렷한 필드(사업자번호·전화·거래일시·주소)는 정규식으로도 안정적으로 뽑을 수 있다 — 이미 1단계 텍스트에 "사업자번호:", "TEL:", "거래일시:", "주소:" 같은 라벨이 명확히 붙어있기 때문이다.

```javascript
function regexFallback(rawText) {
  const bizNoLabeled = rawText.match(/사업자(?:등록)?번호\s*[:：]?\s*(\d{3}[-\s]?\d{2}[-\s]?\d{5})/);
  const phoneMatch = rawText.match(/(?:TEL|전화(?:번호)?)\s*[:：]?\s*([\d\-]{9,13})/i);
  const dateMatch = rawText.match(/거래일시\s*[:：]?\s*([\d]{2,4}[./\-][\d]{1,2}[./\-][\d]{1,2}[^\n]{0,15})/);
  const addrMatch = rawText.match(/주소\s*[:：]?\s*([^\n]+)/);
  return {
    business_reg_no: bizNoLabeled?.[1]?.replace(/\s/g, "") || null,
    phone: phoneMatch ? phoneMatch[1].trim() : null,
    date: dateMatch ? dateMatch[1].trim() : null,
    address: addrMatch ? addrMatch[1].trim() : null,
  };
}
```

실제 실패했던 영수증 원문으로 이 정규식들을 직접 테스트해보니 네 필드 전부 정확히 뽑혔다. 이 결과를 LLM이 비워둔 자리에만 채워 넣는 방식으로 통합했다.

```javascript
if (structured) {
  if (!structured.phone && regexCheck.phone) structured.phone = regexCheck.phone;
  if (!structured.date && regexCheck.date) structured.date = regexCheck.date;
  if (!structured.address && regexCheck.address) structured.address = regexCheck.address;
}
```

## STEP 4: 금액 필드는 백필 대상에서 뺐다 — 그리고 나중에 재검토했다

`total`(합계금액)은 처음엔 안전망 백필 대상에 넣지 않았다. 숫자 필드, 특히 금액은 잘못 채우면 신뢰도에 미치는 영향이 커서, "LLM 결과와 정규식 결과가 다르면 경고만 띄우고 자동으로 바꾸지는 않는다"는 보수적인 방침을 세웠다.

```javascript
document.getElementById("rcpWarn").textContent =
  (rc && rc.total != null && data.structured.total != null && rc.total !== data.structured.total)
    ? t("rcp_warn_total") : "";
```

반면 `business_reg_no`(사업자등록번호)는 처음엔 이것도 "숫자류 필드"라며 같이 보수적으로 뒀는데, 나중에 실사용 중 "사업자등록번호"가 아니라 "사업자번호"로만 표기된 영수증에서 LLM이 못 찾는 사례가 나왔다. 이때 재검토했다 — 사업자번호는 금액과 달리 **형식이 고정적(3-2-5자리 숫자)이라 오탐 위험이 낮고, 잘못 채워져도 금액처럼 재무적 영향이 없다.** 같은 "숫자 필드"라도 리스크 성격이 다르면 다른 정책을 적용해야 한다는 걸 이때 재확인하고, 사업자번호는 백필 대상에 포함시켰다.

## STEP 5: 잘못된 항목 분류도 같이 고쳤다

같은 검토 과정에서 또 다른 문제도 발견했다 — 카드 결제 전표에서 "[일시불]"이라는 결제 방식 표시가 품목(item)으로 잘못 분류되고 있었다. 이건 안전망으로 고칠 문제가 아니라 애초에 프롬프트 지시가 불명확했던 것이라, 프롬프트 자체를 수정했다.

```
"카드 결제 전표(매출표)처럼 실제 구매 품목 목록이 없는 영수증이면 빈 배열로
두세요 — [일시불]/[할부] 같은 결제 방식 표시는 품목이 아니니 items에 넣지
마세요."
```

## ✅ 완료 확인

- [ ] JSON 파싱 성공 + 필드 공백이라는 "조용한 실패" 유형을 재현·확인
- [ ] 라벨이 뚜렷한 필드(사업자번호·전화·주소·거래일시)에 정규식 안전망 추가
- [ ] 금액처럼 리스크가 큰 필드는 자동 백필 대신 대조·경고로 보수적으로 처리
- [ ] 형식이 고정적이고 재무 영향이 없는 필드는 재검토 후 백필 대상에 포함
- [ ] 결제방식 표시가 품목으로 오분류되는 프롬프트 문제 별도 수정
