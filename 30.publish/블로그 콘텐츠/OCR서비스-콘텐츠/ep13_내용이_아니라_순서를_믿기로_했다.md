# EP13: "고치려고 클릭했는데 못 찾는다"는 모순 — 내용 대신 순서를 믿기로 했다

**시리즈**: OCR 서비스구축 #13
**이 글을 읽고 나면**: "내용이 일치해야 위치를 찾을 수 있다"는 가정이 왜 순환논리에 빠지는지, 그리고 편집거리 기반 근사매칭 대신 순서·글자수만으로 위치를 계산하는 방식이 왜 더 견고한 대안이 될 수 있는지 알 수 있습니다.

---

## 핵심 한 줄 요약
> 박스를 클릭했을 때 본문에서 그 위치를 찾는 로직을 "내용이 비슷한 부분을 찾는다"로 만들었더니, 정확히 고쳐야 할 자리(본문이 크게 틀린 곳)에서 가장 자주 실패했다. 사용자의 한 마디—"내용이 일치해야 찾아진다는 건 모순 아니냐"—가 설계를 완전히 뒤집었고, 최종적으로는 내용을 전혀 비교하지 않고 박스의 순서와 글자 수만으로 위치를 계산하는 방식으로 다시 만들었다.

> **자주 묻는 질문**
> **Q. 크롭을 재인식하는 방식(EP12)에는 무슨 문제가 있었나요?** → 같은 모델(olmOCR-2)이라도 문맥 없이 아주 작은 조각(글자 몇 개)만 잘라서 주면 인식 품질이 크게 떨어지는 사례가 실기기 테스트에서 나왔다. 손글씨 메모 한 단어를 크롭해서 재인식했더니 전체 이미지를 인식했을 때보다 훨씬 엉뚱한 텍스트가 나왔다.
> **Q. "내용이 일치해야 찾아진다"가 왜 모순인가요?** → 박스를 클릭하는 이유 자체가 "그 자리 인식이 틀렸으니 고치려는 것"이다. 그런데 위치를 찾는 조건이 "본문과 내용이 비슷해야 한다"이면, 본문이 심하게 틀린 자리일수록(=가장 고쳐야 할 자리일수록) 오히려 못 찾을 확률이 높아진다.
> **Q. 편집거리 매칭을 아예 버리고 순서·글자수만 쓰면 오차가 안 생기나요?** → 생긴다. EasyOCR이 특정 박스에서 글자를 실제보다 더 많이 인식하거나 빠뜨리면 그 이후 박스들 위치가 밀린다. 다만 그 오차는 근처 박스에만 국지적으로 영향을 주고 전체 문서에 누적되지는 않는다는 걸 재현 테스트로 확인했다 — "가끔 몇 글자 어긋날 수 있는 방식"과 "특정 조건에서 아예 못 찾는 방식" 중 전자를 택한 셈이다.

---

## 문제 상황

EP12에서 만든 "정밀 교정" 기능은 EasyOCR로 텍스트 위치(박스)만 찾고, 박스를 클릭하면 그 영역을 크롭해 이미 검증된 올mOCR-2로 다시 인식하는 하이브리드 구조였다. 실기기로 테스트해보니, 이 구조 자체에서 시작해 연속으로 세 가지 문제가 드러났다.

## STEP 1: 크롭 재인식이 전체 인식보다 더 나쁘다

사용자가 손글씨 메모("은행 다녀오기 / 화분 물 주기")를 촬영해 테스트했다. 전체 이미지 인식 결과는 대부분 정확했지만 "다녀오기"를 "대기하기"로 잘못 읽었다(4글자 중 3글자가 다름). 그 오인식된 자리를 고치려고 정밀 교정 모드에서 박스를 클릭해 크롭 재인식을 시켜보니, 결과가 "다녀오기"→"따가57" 같은 전혀 엉뚱한 텍스트로 나왔다.

원인은 문맥이었다. 크롭된 이미지는 손글씨 한두 단어만 담긴 아주 작은 조각이라, 같은 모델이라도 주변 맥락(다른 글자들, 전체 레이아웃) 없이는 인식 정확도가 크게 떨어졌다. 사용자의 요청은 명확했다 — "동일 모델을 써서 더 좋은 결과를 내도록 하던가 아니면 재인식을 하지 않는게 좋겠어."

## STEP 2: 크롭 재인식을 버리고, "내용으로 찾기"로 전환

크롭 재인식을 완전히 없애기로 했다. 대신 EasyOCR이 자체적으로 반환하던 `hint_text`(신뢰도 낮아 그동안 버려두던 값)를 검색 키로 재활용했다 — "글자 그대로는 못 믿어도, 위치 힌트로는 쓸모 있다"는 논리였다. 편집 거리(레벤슈타인) 기반 근사매칭으로, 이미 검증된 전체 본문 텍스트 안에서 그 박스에 해당하는 구간을 찾았다.

```javascript
function fuzzyFitMatch(haystack, needle) {
  // 표준 "free-start 근사 문자열 매칭" DP — haystack 어디서 시작해도 비용 0
  let prevCost = new Array(haystack.length + 1).fill(0);
  // ... 편집 거리 계산 후 최소 비용 구간의 시작/끝 반환
}
```

박스 위치(세로 비율)로 본문 안 예상 구간을 먼저 좁히고, 그 안에서 편집거리 비율이 임계값 이내면 매칭으로 인정하는 2단계 구조였다. 그럴듯해 보였다.

## STEP 3: "못 찾음"이 곧 "수정도 못 함"이라는 막다른 길

사용자가 다시 테스트했다. 이번엔 정확히 EP12의 그 예시—"다녀오기"가 "대기하기"로 오인식된 자리—를 고치려고 박스를 클릭했다. 결과는 "본문에서 이 위치에 해당하는 문구를 찾지 못했습니다"라는 에러였다.

더 큰 문제는 그다음이었다. 사용자가 편집 필드에 직접 "다녀오기"를 입력하고 "본문에 반영"을 눌렀는데도 계속 같은 에러가 났다 — "본문에서 수정이 되지도 않아. 막혀있어." 매칭이 실패하면 본문의 어느 위치를 바꿔야 할지 아는 정보(`_lastMatchSpan`)가 아예 없었기 때문에, 편집 필드에 뭘 입력하든 반영할 방법이 없는 구조였다.

## STEP 4: 사용자의 지적 — "내용이 일치해야 찾아진다는 게 모순 아니냐"

사용자에게 왜 매칭이 실패하는지 설명하면서("다녀오기" vs "대기하기"는 4글자 중 3글자가 달라 어떤 임계값을 잡아도 편집거리 매칭이 실패한다), 매칭 정확도를 높이는 방향으로 개선을 제안했다. 그런데 돌아온 답은 문제를 완전히 다른 각도에서 짚었다.

> "박스를 클릭했을 때 본문에서 위치를 못찾을 수 없을 것 같은데... 내용을 수정하려고 클릭하는데 내용이 일치하지 않아서 못찾는다는건 논리 모순인것 같아."

정확한 지적이었다. 박스를 클릭하는 목적 자체가 "그 자리 인식이 틀렸으니 고치려는 것"인데, "내용이 비슷해야 위치를 찾는다"는 조건은 정확히 그 목적과 충돌한다. 본문이 심하게 틀린 자리일수록 고쳐야 할 필요성은 크지만, 편집거리 기반 매칭은 그런 자리일수록 실패할 확률이 높다 — 설계가 스스로 발목을 잡는 구조였다.

## STEP 5: 내용 대조를 버리고, 순서와 글자 수만으로 위치를 계산

사용자가 제안한 대안은 단순했다 — 박스가 몇 번째이고 몇 글자로 인식됐는지만 알면, 앞에서부터 누적해서 "이 박스는 본문의 N~M번째 글자"라고 계산할 수 있지 않냐는 것이었다. 실제로 구현해보니 타당했다.

```javascript
function orderBoxesForReadingOrder(boxes) {
  // 세로 위치로 먼저 정렬 → 세로 중심이 가까운 것끼리 "같은 줄"로 묶고
  // 같은 줄 안에서는 가로 위치로 재정렬 (위→아래, 왼→오 읽기 순서)
}

function assignBoxOffsets(orderedBoxes, bodyStrippedLen) {
  const lens = orderedBoxes.map(b => Math.max(1, (b.hint_text || "").replace(/\s+/g, "").length));
  const total = lens.reduce((a, c) => a + c, 0);
  const scale = total > 0 && bodyStrippedLen > 0 ? bodyStrippedLen / total : 1;
  let cursor = 0;
  orderedBoxes.forEach((box, i) => {
    box._offStart = Math.round(cursor * scale);
    cursor += lens[i];
    box._offEnd = Math.round(cursor * scale);
  });
}
```

핵심은 두 가지다. 첫째, 내용을 전혀 비교하지 않는다 — 박스 하나가 몇 글자였는지(길이)와 몇 번째였는지(순서)만 쓴다. 둘째, 박스 전체 글자 수 합과 본문 실제 길이가 다를 수 있어서(둘 다 독립적인 인식 오차가 있으므로) 비율로 스케일 보정한다.

재현 테스트로 검증했다. 본문이 "대기하기"로 오인식된 자리에, EasyOCR 힌트가 정답("다녀오기")이든 오답이든 상관없이 — 순서와 길이만으로 정확히 그 자리를 가리켰다.

```
은행 -> off: 0 2   selected: "은행"
다녀오기 -> off: 2 6   selected: "대기하기"   ← 내용은 안 봤지만 위치는 정확
화분 -> off: 6 8   selected: "화분"
```

특정 박스 하나가 글자 수를 실제보다 적게 인식한 경우도 테스트했다. 그 오차는 바로 다음 박스로 국지적으로 전파될 뿐, 멀리 떨어진 박스들(스케일 보정 덕분)에는 영향을 주지 않았다.

## STEP 6: UI까지 같이 단순화했다가 되돌린 실수

새 매칭 로직을 넣으면서, 편집 필드와 "본문에 반영" 버튼으로 이뤄진 기존 UI를 "본문 텍스트 영역에서 바로 선택"하는 방식으로 같이 바꿔버렸다. 매칭 로직 개선과 UI 구조 변경은 별개 결정이었는데, 한 번에 묶어서 바꾼 게 실수였다.

> "이게 뭐야... 대기하기를 다녀오기로 수정할 수 있게 해당 위치를 클릭하면 이미지 보여주고 기존처럼 수정할수 있는 필드를 보여줘야지. 왜 있던것이 없어졌어."

썸네일과 편집 필드, "본문에 반영" 버튼을 원래대로 복원했다. 다만 그 필드를 채우는 로직만 새 오프셋 기반 위치 계산으로 바꿔뒀다 — 매칭이 실패해서 완전히 막히던 이전 버그는 재도입하지 않으면서, 사용자가 기대했던 화면 구조는 그대로 유지하는 형태로 정리됐다.
