# EP05: 최신 논문(문서 디워핑)까지 검증했지만 도입하지 않은 이유 + 배포 자동화 회고

**시리즈**: OCR 서비스구축 #5 (완결)
**이 글을 읽고 나면**: "논문에서 좋다고 하는 전처리 기법"을 내 파이프라인에 붙이기 전에 반드시 통제 실험으로 검증해야 하는 이유와, 로컬 PC 기반 AI 서비스를 실제로 배포·운영하는 전체 흐름을 알 수 있습니다.

---

## 핵심 한 줄 요약
> 최신 문서 디워핑(dewarping) 모델을 실제로 설치해 통제 실험을 해보니, 이미 강력한 VLM(olmOCR-2)에는 오히려 정확도를 깎아먹었다 — "논문이 좋다고 한다"와 "내 파이프라인에 도움이 된다"는 다른 이야기다.

> **자주 묻는 질문**
> **Q. 디워핑(dewarping)이 뭔가요?** → 구겨지거나 휘어진 종이를 사진으로 찍었을 때, AI로 평평하게 펴서 인식률을 높이는 전처리 기법이다.
> **Q. 그럼 구겨진 영수증 문제는 그냥 포기하나요?** → 아니다. 대신 "반복 폭주가 감지되면 사용자에게 재촬영을 안내"하는 더 실용적인 대응으로 방향을 바꿨다(EP04에서 만든 신호를 재활용).
> **Q. 왜 부정적인 결과도 블로그에 쓰나요?** → "이 방법은 안 통했다"는 정보도 다음에 같은 실험을 반복하지 않게 해주는 값진 데이터이기 때문이다.

---

## 문제 상황

배포 후 실사용 테스트에서 반응은 좋았다 — "구겨진 영수증 빼고는 인식률이 매우 좋았다." 남은 약점은 딱 하나, 구겨진 영수증이었다. 최신 논문까지 찾아보기로 했다.

## STEP 1: 최신 문서 디워핑 연구 조사

D2Dewarp(2025), DocTr++(2026), UVDoc 세 가지가 눈에 띄었다. 문제는 D2Dewarp와 DocTr++는 사전학습 가중치가 **Google Drive/Baidu Cloud로만 배포**돼서 자동화된 다운로드가 사실상 불가능했다. UVDoc은 달랐다 — **PaddleOCR 패키지에 내장돼 HuggingFace에서 자동 다운로드**되는 구조였다.

```bash
pip install paddleocr paddlepaddle
```

```python
from paddleocr import TextImageUnwarping
model = TextImageUnwarping(model_name='UVDoc')
result = model.predict('receipt.jpg')
```

## STEP 3: 통제 실험 설계 — "느낌"이 아니라 재현 가능한 왜곡으로

실사용자가 찍은 "그" 구겨진 영수증 사진은 수중에 없었다. 대신 **정답을 이미 확보해둔 깨끗한 영수증에 합성 왜곡을 입혀서** 재현 가능한 실험으로 만들었다.

```python
# 물결 왜곡 — 실제 종이 주름과 비슷한 국소 비선형 변위
yy, xx = np.meshgrid(np.arange(h), np.arange(w), indexing='ij')
dx = 10*np.sin(yy*0.02+1) + 6*np.sin(yy*0.05+2.5) + 4*np.sin(xx*0.03)
dy = 8*np.sin(xx*0.018+0.5) + 5*np.sin(xx*0.04+1.8) + 3*np.sin(yy*0.025)
warped = cv2.remap(img, (xx+dx).astype(np.float32), (yy+dy).astype(np.float32), cv2.INTER_LINEAR)
```

## STEP 4: 결과 — 디워핑이 오히려 정확도를 깎았다

| 조건 | CER |
|------|-----|
| 합성 왜곡 원본 그대로 OCR | 0.246 |
| **UVDoc 디워핑 후 OCR** | **0.281 (악화)** |

시각적으로 봐도 디워핑 후 이미지가 눈에 띄게 평평해지지 않았다 — UVDoc은 책을 스캔할 때 생기는 매끄러운 곡률 왜곡에 최적화된 모델이라, 종이 주름 같은 고빈도·불규칙 왜곡에는 학습 분포 밖이었을 가능성이 높다. 게다가 리샘플링 과정에서 생기는 미세한 흐림이 오히려 손해였다.

추가로 조명(그림자) 왜곡도 합성해서 별도로 테스트했는데, **olmOCR-2는 이미 그림자 얼룩에도 상당히 강건**해서(CER 0.169, 원본보다 오히려 낮음) 보정할 여지 자체가 거의 없었다.

## STEP 5: 결론 — 별도 인프라 대신 기존 신호를 재활용

디워핑을 프로덕션에 넣으려면 PC에 상시 파이썬 서비스를 하나 더 띄우고, Cloudflare Tunnel 라우팅을 확장하고, Worker에서 한 단계를 더 호출해야 한다 — 실측으로 이득이 없는데 이 복잡도를 감수할 이유가 없었다. **"최신 논문 기법을 통제 실험으로 검증한 뒤 도입하지 않기로 결정"** 하는 것도 엔지니어링 판단이다.

대신 EP04에서 만든 `low_confidence` 신호를 그대로 재활용했다 — 반복 폭주가 감지된 경우, 결과는 그대로 보여주되 재촬영을 안내하는 문구를 덧붙였다.

```js
low_confidence_tip: "⚠ 원본이 흐릿하거나 구겨져 있어 인식이 불안정할 수 있습니다. 최대한 평평하게 펴서 밝은 곳에서 다시 촬영하거나, 회전 버튼으로 다시 시도해 보세요."
```

## STEP 6: 배포 자동화 — Worker + 정적 사이트 2단 배포

이 서비스는 두 파트로 나뉜다. **Cloudflare Worker**(추론 게이트웨이)와 **정적 사이트**(브라우저 UI)는 배포 방식이 다르다.

```bash
# 1) Worker 배포
cd workers/ocr-service
npx wrangler deploy
```

```powershell
# 2) 정적 사이트 배포 (test → staging → www 순서 권장)
.\deploy.ps1 -Target 1
```

`deploy.ps1`은 배포마다 자동으로: 버전 증가 → NAS 백업 → tar+SSH 전송 → Cloudflare Edge 캐시 퍼지까지 처리한다. 버전 관리는 `MAJOR.MINOR.PATCH.BUILD` 형식으로, 환경별로 증가하는 자리가 다르다(test는 BUILD, staging은 PATCH, www는 MINOR).

```bash
git add workers/ocr-service/index.js service/ocr/index.html deploy.ps1
git commit -m "feat(ocr): olmOCR-2 교체 + 다운스케일 + repeat_penalty 재시도"
```

## 최종 결과 요약

| 항목 | 목표 | 실제 결과 |
|------|------|-----------|
| 손글씨 | 90%+ | **97.4~99.8%** |
| 스캔 문서(표 포함) | 100% | 80.5% (표 전체 인식, 헤더·푸터 잔글씨만 누락) |
| 영수증 사진 | 90%+ | 78~83% (핵심 데이터는 매번 정확) |

세 목표 중 손글씨는 초과 달성, 스캔 문서·영수증은 목표엔 못 미쳤지만 실사용 반응은 긍정적이었다 — **문자 단위 정확도(CER)와 실사용 만족도가 항상 일치하진 않는다**는 것도 이번 시리즈의 소득이다.
