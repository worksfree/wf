# EP09: 파일 하나와 폴더 통째로는 완전히 다른 UI가 필요했다 — 배치 처리 설계

**시리즈**: OCR 서비스구축 #9
**이 글을 읽고 나면**: 단건 처리와 배치(다건) 처리를 하나의 UI로 억지로 합치지 않고 왜 분리해야 하는지, 그리고 "예상 남은 시간"을 복잡한 예측 모델 없이 실시간 이동평균만으로 꽤 쓸만하게 계산하는 방법을 알 수 있습니다.

---

## 핵심 한 줄 요약
> 단건 처리는 "결과를 바로 확인하고 다듬는" 흐름이고 다건 처리는 "맡겨두고 기다리는" 흐름이다 — 목적이 다르니 화면도 달라야 했다. 설정(대비·샤프니스·문서유형)은 두 모드가 공유하되, 결과 확인 방식과 진행 상황 표시는 완전히 분리해서 설계했다.

> **자주 묻는 질문**
> **Q. 왜 처음부터 하나의 화면으로 안 만들었나요?** → 처음엔 그럴 생각이었는데, 실제로 파일 1개를 올릴 때와 50개를 올릴 때 사용자가 보고 싶어하는 정보 자체가 다르다는 걸 깨달았다. 파일 1개면 "결과가 정확한지" 확인하고 싶고, 50개면 "얼마나 남았는지, 실패한 게 있는지"가 궁금하다.
> **Q. 예상 남은 시간은 어떻게 계산하나요?** → 복잡한 예측 모델이 아니라, 지금까지 처리 완료된 파일들의 평균 처리 시간에 남은 파일 개수를 곱하는 단순한 방식이다. 처리가 진행될수록(표본이 쌓일수록) 정확도가 자연스럽게 올라간다.
> **Q. 설정(대비·샤프니스 등)은 왜 공유하나요?** → 단건에서 파일 하나로 설정을 미리 확인한 뒤 "이 설정이 괜찮네"라고 판단하고 나서 다건으로 넘어가는 흐름을 의도했다. 설정이 모드마다 따로면 단건에서 확인한 게 다건에 그대로 안 넘어가서 다시 조정해야 하는 번거로움이 생긴다.

---

## 문제 상황

OCR 서비스를 "영수증 한 장 빠르게 텍스트로 바꾸기"에서 "폴더 통째로 일괄 처리하기"까지 지원하려니, 하나의 업로드 버튼과 하나의 결과 영역만으로는 부족했다. 파일 1개 처리와 파일 50개 처리는 사용자가 화면에서 기대하는 정보 자체가 다르다.

## STEP 1: 두 모드를 탭으로 분리

기존에 만들어둔 QR 생성기 서비스가 이미 같은 문제(단건 생성 vs 대량 생성)를 겪었고, 탭으로 분리하는 패턴을 검증해둔 상태였다. 이 패턴을 그대로 재사용했다.

```html
<div class="mode-tabs">
  <button class="mode-tab active" onclick="switchMode('single')">단건 처리</button>
  <button class="mode-tab" onclick="switchMode('bulk')">다건 처리</button>
</div>

<div id="modeSingle"> ... 단건 UI ... </div>
<div id="modeBulk" style="display:none;"> ... 다건 UI ... </div>
```

```javascript
function switchMode(mode) {
  document.getElementById("modeSingle").style.display = mode === "single" ? "" : "none";
  document.getElementById("modeBulk").style.display = mode === "bulk" ? "" : "none";
  document.getElementById("tabSingle").classList.toggle("active", mode === "single");
  document.getElementById("tabBulk").classList.toggle("active", mode === "bulk");
}
```

## STEP 2: 설정 패널은 두 모드 밖에 — 공유 상태로

대비·샤프니스·문서유형·출력형식 같은 설정은 탭 내부가 아니라 탭 바깥, 항상 보이는 위치에 뒀다. 두 모드가 같은 DOM 엘리먼트(같은 `id`의 슬라이더 등)를 그대로 참조하기 때문에, 상태를 동기화하는 코드를 따로 짤 필요가 없었다 — 애초에 하나의 값을 공유하니까.

```html
<div class="settings-panel">
  <!-- 대비/샤프니스/문서유형/출력형식 슬라이더 — 단건·다건 공용 -->
</div>
<div class="settings-shared-hint">
  이 설정은 단건·다건 처리에 공통 적용됩니다. 단건에서 파일 하나로 미리 결과를
  확인한 뒤 다건으로 넘어가면 같은 설정으로 처리됩니다.
</div>
```

의도한 사용 흐름은 이렇다: 사용자가 먼저 단건 모드에서 파일 하나로 대비·샤프니스를 조절해가며 결과를 확인하고 만족스러운 설정을 찾은 다음, 다건 모드로 전환해서 나머지 수십 장을 그 설정 그대로 처리한다. 힌트 문구로 이 흐름을 명시적으로 안내했다.

## STEP 3: 다건 처리의 핵심 — 예상 남은 시간

파일 50개를 올려두고 아무 정보 없이 기다리게 하는 건 나쁜 경험이다. "지금 몇 번째까지 됐고, 앞으로 얼마나 걸릴지"를 보여주기로 했다.

정확한 예측을 하려면 복잡한 모델이 필요하겠지만, 여기서는 단순하게 접근했다 — **지금까지 완료된 파일들의 평균 처리 시간 × 남은 파일 개수.**

```javascript
function updateProgressEls(els, completed, total, durations, done) {
  const pct = total ? Math.round((completed / total) * 100) : 0;
  els.progress.value = pct;
  if (done) { els.eta.textContent = ""; return; }
  if (durations.length >= 1) {
    const avg = durations.reduce((a, b) => a + b, 0) / durations.length;
    els.eta.textContent = t("batch_eta")(formatDuration(avg * Math.max(0, total - completed)));
  } else {
    els.eta.textContent = t("batch_eta_calculating");
  }
}
```

`durations` 배열에 파일 하나 처리할 때마다 걸린 시간(초)을 계속 쌓고, 평균을 낸다. 첫 파일이 끝나기 전(durations가 비어있을 때)은 "계산 중..."이라고만 표시한다 — 표본이 0개인데 억지로 숫자를 보여주면 오히려 신뢰가 떨어지기 때문이다.

## STEP 4: 이 단순한 방식이 왜 충분했나

더 정교하게 만들려면 파일 크기별 가중치, 이동평균의 지수감쇠(최근 파일에 더 큰 가중치) 같은 걸 넣을 수도 있었다. 그런데 실제로 처리 시간의 변동 폭이 크지 않은 워크로드(같은 모델, 비슷한 크기의 이미지들)라서, 단순 산술평균만으로도 체감상 충분히 정확했다. 파일 5개쯤 처리되고 나면 평균이 안정되고, 그 뒤로는 예측이 크게 틀리지 않았다.

**정교한 예측 모델을 미리 만드는 것보다, "표본이 쌓일수록 자연스럽게 정확해지는 단순한 방식"으로 시작하고 실제로 부족하다는 신호가 나오면 그때 고도화하는 게** 이 규모의 기능에는 맞는 선택이었다.

## STEP 5: 실패한 파일도 진행률에 포함시키기

배치 처리 중 일부 파일이 실패(예: 손상된 PDF, 지원하지 않는 형식)해도 전체 배치가 멈추지 않게 만들었다. 실패한 파일도 "처리 완료"로 카운트하고 별도로 실패 목록에 기록하는 방식이다 — 실패 하나 때문에 진행률이 멈춰버리면, 파일 50개 중 하나가 잘못됐다는 이유로 나머지 49개 결과까지 못 받는 상황이 된다.

```javascript
if (resp.status === 429 || data.error === "rate_limited") { stoppedReason = "rate_limited"; durations.push((performance.now() - t0) / 1000); break; }
if (resp.status === 503 || data.error === "pc_offline") { stoppedReason = "pc_offline"; durations.push((performance.now() - t0) / 1000); break; }
```

다만 요청 제한(rate limit)이나 PC 오프라인처럼 "이 파일만의 문제가 아니라 이후 파일도 다 실패할 게 뻔한" 상황은 예외다 — 이런 경우는 배치를 멈추고 사용자에게 이유를 명확히 알려준다. "개별 파일 실패는 계속 진행, 구조적 실패는 즉시 중단"으로 구분한 것이다.

## ✅ 완료 확인

- [ ] 단건/다건 탭 분리, 설정 패널은 공유 상태로 유지
- [ ] 이동평균 기반 예상 남은 시간 계산(durations 배열 누적)
- [ ] 표본 0개일 때 "계산 중" 표시로 신뢰도 낮은 추정치 노출 방지
- [ ] 개별 파일 실패는 배치 계속 진행, 구조적 실패(요청 제한·서버 오프라인)는 즉시 중단
