# EP13: 클릭 한 번으로 테스트하기 — 샘플 갤러리와 라이선스 다시 점검하기

**시리즈**: OCR 서비스구축 #13 (완결편)
**이 글을 읽고 나면**: "테스트하기 쉽게 샘플 몇 장 추가하자"는 작은 개선을 실제로 구현할 때, 이미 확보해둔 테스트 데이터 전체를 그대로 재사용하면 안 되는 이유와 라이선스를 다시 점검하는 실무 과정을 알 수 있습니다.

---

## 핵심 한 줄 요약
> 개발 중 테스트에 쓴 298장의 이미지 중 실제로 웹페이지에 공개 게시해도 되는 건 29장뿐이었다. 나머지 269장(대부분)은 "로컬 R&D 테스트 용도로만" 사용이 확인된 데이터라, 재배포 라이선스가 명확한 CC-BY-4.0 표본만 골라 갤러리를 만들었다.

> **자주 묻는 질문**
> **Q. 298장 중 269장을 왜 못 쓰나요?** → 이 데이터셋(KORIE, 286장)은 학술 벤치마크로 공개돼 있지만 README에 재배포 조건이 명시돼 있지 않았다. 로컬에서 정확도를 재는 용도로는 문제없이 썼지만, 그건 "내 컴퓨터 안에서 테스트"와 "누구나 접속 가능한 웹페이지에 올리는" 건 완전히 다른 사용 범위다.
> **Q. 라이선스가 없으면 왜 재배포하면 안 되나요?** → 저작권은 기본적으로 "명시적으로 허락받은 것만" 할 수 있다는 원칙이다. 라이선스가 명시 안 된 데이터는 "안 된다고 안 써있으니 돼도 된다"가 아니라 "된다고 안 써있으니 안 하는 게 안전하다"로 해석해야 한다.
> **Q. 샘플을 클릭하면 실제로 어떻게 동작하나요?** → 서버에 미리 올려둔 이미지 파일을 `fetch()`로 받아서 File 객체로 감싼 다음, 사용자가 직접 업로드했을 때와 완전히 동일한 코드 경로(`handleFile()`)로 처리한다. 샘플 전용 특수 로직이 따로 없다 — 업로드 파이프라인 전체를 그대로 검증하는 셈이다.

---

## 문제 상황

이 시리즈를 쓰면서 매번 로컬 파일탐색기에서 테스트용 이미지를 찾아 업로드하는 게 번거로웠다. "화면에 샘플 몇 개를 썸네일로 띄워두고 클릭 한 번으로 테스트할 수 있게 하자"는 아이디어가 나왔다 — 개발 중 이미 실측 검증에 써온 파일들이 있으니 그걸 그대로 쓰면 될 거라 생각했다.

## STEP 1: 기존 테스트 코퍼스 매니페스트를 다시 열어봤다

이 서비스의 정확도를 검증하려고 298장짜리 테스트 코퍼스를 이미 만들어둔 상태였다(EP02의 모델 비교, EP06·EP07의 그리드 서치에 쓴 이미지들의 상위 집합). "샘플 갤러리에 이 중 몇 장만 골라 쓰면 되겠다" 싶어서, 먼저 출처 매니페스트를 다시 확인했다.

```markdown
| 폴더 | 장수 | 출처 | 라이선스 |
|---|---|---|---|
| receipt/korie_*     | 286 | KORIE(학술 벤치마크)      | 명시 없음 — 재배포 전 저자 확인 권장 |
| receipt/hf_*         | 20  | HumynLabs(HuggingFace)  | CC-BY-4.0 |
| handwriting/hf_*     | 9   | HumynLabs(HuggingFace)  | CC-BY-4.0 |
| document/hf_*        | 3   | Kratos-AI(HuggingFace)  | 명시 없음 |
```

298장 중 286장(압도적 대부분)을 차지하는 KORIE는 "로컬 R&D 테스트 용도로 사용"이라고 스스로 명시해뒀던 것을 다시 발견했다 — 애초에 처음 데이터를 확보할 때 이렇게 조건을 달아 기록해둔 게, 나중에(지금) 다른 용도로 재사용하려 할 때 실수를 막아준 셈이다.

## STEP 2: "로컬 테스트"와 "공개 게시"는 다른 기준이라는 걸 재확인

KORIE 데이터를 내 컴퓨터에서 그리드 서치에 쓰는 것과, 그 이미지를 `test.worksfree.kr` 같은 공개 웹페이지에 올려서 누구나 다운로드할 수 있게 만드는 건 완전히 다른 사용 범위다. 전자는 이미 "확인"까지 마친 용도였고, 후자는 새로운 결정이 필요한 영역이었다.

라이선스가 명시된(CC-BY-4.0) HumynLabs의 두 데이터셋만 후보로 남았다 — 영수증 20장, 손글씨 9장, 합쳐서 29장. Kratos-AI 문서셋(3장)은 라이선스 명시가 없어서 이번에도 제외했다.

## STEP 3: 29장 중 4장만 추려서 갤러리로

전체 29장을 다 갤러리에 올릴 필요는 없었다 — 각 카테고리에서 대표성 있는 2장씩만 골랐다(영수증 2장, 손글씨 2장). 이미지 하나당 1~1.4MB 정도라, 4장이면 페이지 로딩 부담도 크지 않았다.

```html
<button class="sample-thumb" data-sample="samples/sample_receipt1.jpg" data-name="샘플_영수증1.jpg">
  <img src="samples/sample_receipt1.jpg" alt="" loading="lazy">
  <span>영수증</span>
</button>
```

`loading="lazy"`를 붙여서, 사용자가 실제로 이 갤러리 영역까지 스크롤하기 전에는 이미지를 미리 받지 않게 했다 — 작은 최적화지만 페이지 초기 로딩에 불필요한 부담을 주지 않는다.

## STEP 4: 클릭하면 실제 업로드와 똑같은 코드 경로를 태운다

샘플 갤러리 전용 처리 로직을 새로 만들지 않고, 기존 파일 업로드 핸들러를 그대로 재사용했다.

```javascript
document.querySelectorAll(".sample-thumb").forEach((btn) => {
  btn.addEventListener("click", async () => {
    const url = btn.dataset.sample;
    const name = btn.dataset.name;
    const resp = await fetch(url);
    const blob = await resp.blob();
    const file = new File([blob], name, { type: blob.type || "image/jpeg" });
    await handleFile(file);  // 실제 업로드했을 때와 완전히 동일한 함수
  });
});
```

서버의 샘플 이미지를 `fetch`로 받아서 `File` 객체로 감싼 다음, 사용자가 파일 선택창에서 직접 고른 것처럼 만들어 `handleFile()`에 넘긴다. 이렇게 하면 "샘플 클릭"과 "실제 업로드"가 코드 레벨에서 완전히 같은 경로를 타기 때문에, 별도 분기를 유지보수할 필요가 없다 — 업로드 로직이 바뀌면 샘플 갤러리도 자동으로 같이 검증된다.

## STEP 5: 출처를 코드 옆에 남겨두기

나중에 다시 이 갤러리를 손볼 사람(자신 포함)이 "이 이미지 어디서 났지, 더 추가해도 되나?"를 매번 다시 조사하지 않도록, 폴더 안에 라이선스 문서를 같이 남겼다.

```markdown
# 샘플 이미지 출처/라이선스

| 파일 | 출처 | 라이선스 |
|---|---|---|
| sample_receipt1.jpg, sample_receipt2.jpg | HumynLabs/Korean_Receipts_Dataset | CC-BY-4.0 |
| sample_handwriting1.jpg, sample_handwriting2.jpg | HumynLabs/Korean_Handwritten_Notes_Dataset | CC-BY-4.0 |

> 같은 테스트 코퍼스의 KORIE(286장)·Kratos-AI 문서셋은 재배포 라이선스가
> 명시돼 있지 않아 이 공개 갤러리에는 포함하지 않았다.
```
