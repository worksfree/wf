# EP07: CER이 4.19가 나왔다 — OCR이 망가진 게 아니라 채점 기준이 잘못됐다

**시리즈**: OCR 서비스구축 #7
**이 글을 읽고 나면**: 실측 데이터로 모델을 검증할 때 "숫자가 이상하게 나오면 모델을 의심하기 전에 측정 방법 자체를 먼저 의심해야 하는 이유"와, 서로 다른 라벨링 스키마를 가진 여러 데이터셋을 하나의 파이프라인으로 처리하는 실무적인 방법을 알 수 있습니다.

---

## 핵심 한 줄 요약
> AI-Hub 실측 데이터로 재검증하던 중 한 카테고리(유통업)의 CER이 4.19(정상 범위 0~1을 몇 배나 넘음)로 나왔다. 원인을 직접 눈으로 확인해보니 OCR은 실제로 도면을 정확히 읽고 있었고, 문제는 그 데이터셋의 정답 라벨이 "페이지 전체 텍스트"가 아니라 "서식에서 채워진 값만" 담고 있었던 것이었다 — 채점 기준 자체가 다른 걸 재고 있었다.

> **자주 묻는 질문**
> **Q. CER이 1을 넘을 수도 있나요?** → 이론적으로는 가능하다(편집 거리가 정답 길이보다 길면 1을 넘는다). 하지만 실무적으로 "정상적인 OCR 결과"라면 거의 항상 0~1 사이다. 4.19처럼 극단적인 값은 대부분 인식 실패가 아니라 채점 방법 자체의 결함을 의심해야 한다.
> **Q. 다른 두 카테고리(요식·제조)는 왜 문제가 없었나요?** → 그 두 카테고리의 라벨은 페이지 전체를 단어 단위로 라벨링한 방식이라, 정답과 OCR 결과가 같은 대상(전체 페이지)을 가리켰다. 문제가 된 카테고리만 "서식 안내문 제외, 채워진 값만" 라벨링하는 다른 스키마를 썼다.
> **Q. 이 사건에서 얻은 실무적인 교훈은 뭔가요?** → 자동화된 지표(CER 같은)가 하나라도 튀면, 파이프라인 코드부터 의심하기 전에 반드시 원본 데이터(이미지+정답 텍스트+실제 모델 출력)를 사람이 직접 열어봐야 한다는 것. 숫자만 보고 "모델이 나쁘다"고 결론 내렸다면 완전히 잘못된 방향으로 시간을 썼을 것이다.

---

## 문제 상황

EP06에서 로컬 표본 6장(손글씨·긴 문서·영수증)으로 카테고리별 최적 대비/샤프니스를 찾았다. 그런데 표본이 너무 적어서 일반화하기엔 근거가 얕았다. "업종별로도 최적값이 다를까?"를 확인하려고, AI-Hub의 실제 업종별 문서 데이터셋(유통·요식·제조업)을 받아 같은 그리드 서치를 다시 돌렸다.

## STEP 1: 데이터셋 스키마가 4종류로 제각각이었다

AI-Hub에서 받은 원본은 이미지(TS_*.zip)와 라벨(TL_*.zip)이 따로 있는 구조였는데, 데이터셋마다 라벨 JSON의 스키마가 다 달랐다.

```
023(공공행정): Bbox 리스트 형태
056(의약품화장품): annotations → polygons 형태
239: COCO 형식 + attributes.OCR
025(금융및물류): 서식 필드 값 (뒤에서 문제가 되는 지점)
```

스키마별 파서를 따로 만들어서 통일된 형태(이미지 + 정답 텍스트)로 변환하는 전처리 스크립트를 짰다. 데이터셋 하나당 30장씩 샘플링해서 `aihub_samples/{retail,fnb,manufacturing}/`에 채워 넣었다.

## STEP 2: 스윕 실행 — 1212회 호출

EP06과 동일한 그리드(1단계 coarse + 2단계 fine)를 그대로 재사용해서 카테고리당 6개 표본으로 돌렸다.

```
총 호출: 1212건
실패한 호출: 0건
```

## STEP 3: 결과 — 두 카테고리는 정상, 하나는 이상했다

```
fnb(의약품화장품):        콘트라스트 +10%, 샤프니스 100%  →  CER 0.2877
manufacturing(공공행정):   콘트라스트 +20%, 샤프니스   0%  →  CER 0.2835
retail(금융및물류):        콘트라스트 -10%, 샤프니스  73%  →  CER 4.1935
```

fnb·manufacturing은 CER이 0.28대로 정상 범위였다. 그런데 retail만 **4.19** — CER은 원래 0(완벽)~1(전부 틀림) 사이가 정상인데, 4배가 넘는 값이 나왔다. "이 카테고리에서 파라미터를 아무리 바꿔도 OCR이 심각하게 망가지는구나"라고 잠깐 생각했다.

## STEP 4: 숫자만 믿지 않고 실제 결과를 열어봤다

바로 결론 내리지 않고, retail 카테고리의 실제 OCR 출력과 정답 텍스트를 나란히 놓고 읽어봤다.

```
[OCR 실제 출력]
"수신인: ○○물류센터 / 발신인: △△운송 / 본 서식은 화물 운송장 양식입니다.
아래 빈칸에 정확히 기재하여 주십시오. 화물번호: IMG-6-F-0004905 ..."
(페이지 전체 내용을 정확하게, 서식 안내 문구까지 포함해서 읽어냄)

[정답 라벨]
"IMG-6-F-0004905"
(채워진 값 하나만 딱 담겨있음)
```

**OCR은 실제로 서식 전체를 정확하게 읽어내고 있었다.** 문제는 정답 라벨이 "페이지에 실제로 적힌 모든 글자"가 아니라, "서식에서 사람이 채워 넣은 값만" 담고 있었다는 것이다. 채점 알고리즘은 OCR이 뽑아낸 긴 문장과 라벨의 짧은 값 하나를 비교하면서, 둘 다 정확함에도 "거의 다 틀렸다"고 계산해버린 것이다.

## STEP 5: 왜 다른 두 카테고리는 이 문제가 없었나

fnb(056)·manufacturing(023) 데이터셋의 라벨 스키마를 다시 확인해보니, 이쪽은 페이지 전체를 단어 단위로 촘촘하게 라벨링한 방식이었다 — OCR이 읽어낸 대상과 정답 라벨이 가리키는 대상이 정확히 같았다(둘 다 "페이지 전체"). retail(025)만 예외적으로 "서식 필드 값만" 라벨링하는 다른 스키마를 썼던 것이다.

같은 방식으로 채점 파이프라인을 만들어도, **입력 데이터셋의 라벨링 철학이 다르면 같은 지표(CER)가 완전히 다른 걸 측정하게 된다** — 이건 코드 버그가 아니라 데이터 자체의 특성 차이라, 코드를 아무리 들여다봐도 못 찾는다.

## STEP 6: 이 발견을 리포트에 명시적으로 남겼다

수치를 그냥 삭제하거나 조용히 무시하지 않고, 리포트에 왜 무효인지 이유와 함께 명시적으로 남겼다.

```markdown
> **⚠ retail 카테고리 CER 무효**(진단 결과): 이 카테고리에 쓴 025(금융 및
> 물류) 데이터셋 표본이 은행 서식 문서인데, 실제 OCR 출력을 직접 확인해보니
> 양식 문구까지 포함해 전체 페이지를 정확하게 읽어냈다(품질 자체는 정상).
> 그런데 이 데이터셋의 라벨 JSON은 서식 안내 문구는 라벨링하지 않고
> 채워진 필드 값만 담고 있어서, "정답 텍스트"가 실제 페이지 전체 텍스트보다
> 훨씬 짧고 내용도 다르다 — 그래서 CER이 실제 인식 품질과 무관하게
> 비정상적으로 커졌다.
```

나중에 이 리포트를 다시 보는 사람(자기 자신 포함)이 "retail 카테고리는 콘트라스트 -10%가 최선이구나"라고 잘못 믿고 그대로 프로덕션에 반영하는 걸 막기 위해서다. 무효한 측정값도 "왜 무효인지"를 남겨두는 게, 그냥 지워버리는 것보다 훨씬 유용하다 — 같은 실수(이 데이터셋을 다른 목적으로 다시 쓸 때)를 반복하지 않게 해준다.
